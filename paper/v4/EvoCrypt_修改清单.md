## 三、公式及实验表述需要核实或统一的问题

### 1. 第7页公式（2）：明确arg max的优化变量

当前公式为：

$$
v^*(a,b)=\arg\max\{(H_{a,v},v):v\in V_a,\ H_{a,v}\le b\}.
$$

左侧需要返回版本号，而右侧没有显式指定对哪个变量取 arg max。建议改为：

$$
v^*(a,b)=\operatorname*{arg\,max}_{v\in V_a:\,H_{a,v}\le b}(H_{a,v},v).
$$

对应 LaTeX：

```latex
v^*(a,b)=
\operatorname*{arg\,max}_{v\in V_a:\,H_{a,v}\le b}
(H_{a,v},v).
```

保留后文的字典序说明，以及不存在可选版本时返回缺失版本错误的规定。

### 2. 第16页图3：统一时间指标名称

同一时间指标目前采用三种说法：

| 位置 | 当前名称 |
| --- | --- |
| 正文 | `upgrade transaction execution time` |
| 纵轴 | `Upgrade latency (ms)` |
| 图注 | `mean setup latency` |

正文已明确该指标不代表端到端升级延迟。建议纵轴改为 `Upgrade transaction execution time (ms)`，图注改为 `mean upgrade transaction execution time`。若纵轴文字过长，可以合理换行，避免压缩图内字体。第15页关于 `Setup latency` 的表述也应同步检查。

### 3. 第17页图4：澄清毫秒级处理耗时与秒级实验时间轴

正文写作 `Geth-side handling finished within 0.54–2.34 ms`，而图4展示约0–125秒的实验时间轴。这两类数据可以同时成立，但需要明确测量范围，不能仅凭单位差异判断数据错误。

需核实并补充说明：

- 0.54–2.34 ms具体指升级交易处理、事件处理，还是模块准备耗时。
- 图4的秒级时间是否包含节点启动、区块同步和等待激活。
- `Ready` 表示模块准备完成，还是到达激活高度后可调用。

图4中的 `Ready` 大多接近激活时刻，而图2中的 `Ready` 位于激活之前。建议两图中同名状态保持相同含义；若实际含义不同，应修改其中一处名称并说明。

### 4. 第18—19页Table 2：核实原生基线名称

正文说明这些算法不在所评测的预编译合约目录中，但表格对照列为 `Precompile (ms)`，图注使用 `Precompiled Contract`，需要明确基线究竟是什么。

如果实际测量的是独立原生实现，建议统一修改：

| 位置 | 建议名称 |
| --- | --- |
| 表格列名 | `Native (ms)` |
| 表格图注中的比值说明 | `Ratios are WASM/native.` |

如果确实将这些实现接入了自定义预编译合约，则保留相应名称，并补充自定义基线的实现说明，避免读者误以为它们都是客户端已有的预编译合约。
