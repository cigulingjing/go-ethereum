\abstract{Smart contracts increasingly require cryptographic algorithms for authentication, integrity protection, signatures, key agreement, and privacy-preserving workflows. Implementing such algorithms directly in Solidity preserves contract-layer flexibility but can incur high EVM execution and gas overhead, whereas Precompiled Contracts provide efficient native execution but bind algorithm updates to client modification, rebuild, and coordinated deployment. This paper proposes a Cryptographic Coprocessor for the EVM that routes selected contract-facing cryptographic calls to client-side WebAssembly (WASM) modules through a stable invocation interface. The architecture combines on-chain upgrade proposals, off-chain asynchronous WASM preparation, controlled runtime loading, and Activation-Block-based deterministic activation, so that algorithm implementations can be replaced without replacing the whole blockchain client. We implement a Geth prototype and evaluate upgrade efficiency and execution efficiency on a five-node Clique private chain across seven algorithms. In the WASM rerun reported here, all upgrades completed across the five target nodes in 4.86--5.34 s, the post-event readiness tail was at most 287.3 ms, and outputs matched across the WASM-backed Upgrade, Solidity contract, and Precompile paths. The WASM path remained in the same millisecond-scale latency range as Precompiled Contracts for six of seven benchmarks, while SchnorrVerify exposed a clear tail-latency limitation. Upgrade consistency is treated as a protocol security property rather than as a separate experiment. These results indicate that a WASM-based coprocessor boundary can reduce the operational cost of cryptographic algorithm updates while preserving deterministic smart-contract execution under bounded conditions.}

\section{Introduction}\label{sec1}

Blockchain systems are increasingly used in digital finance, supply-chain management, digital identity, and trusted data exchange, and have evolved from narrowly scoped distributed ledgers into programmable trusted computing platforms \cite{nakamoto2008bitcoin,zou2021smartContracts}. Smart contracts provide the core mechanism for this programmability: they execute predefined rules for asset transfer, authorization, state update, and multi-party coordination within a deterministic blockchain execution environment \cite{woodEthereumYellowPaper,ethereumEVM}. These operations commonly depend on cryptographic functions for identity authentication, data integrity, digital signatures, and privacy protection, so smart contracts require ways to invoke or execute cryptographic algorithms to support trustworthy on-chain business logic. At the same time, advances in quantum computing challenge the long-term security assumptions of deployed public-key cryptography \cite{shor1999,grover1996}, and the standardization of post-quantum cryptographic algorithms has made post-quantum migration an important requirement for long-term blockchain security \cite{nistPqcProject}. Because many on-chain workflows expose cryptographic capabilities through smart contracts, this migration requires not only support for new cryptographic algorithms in the underlying blockchain client but also timely access to these capabilities from smart contracts. Providing extensible and evolvable support for contract-facing cryptographic algorithms has therefore become an important problem for blockchain systems designed for long-term security evolution.

Ethereum currently offers two common routes for executing cryptographic logic. A developer can implement an algorithm directly in Solidity, which keeps the logic flexible and deployable at the contract layer but executes the computation through Ethereum Virtual Machine (EVM) instructions \cite{woodEthereumYellowPaper,ethereumEVM}. Gas is the protocol mechanism that prices instruction-level computation and resource use \cite{woodEthereumYellowPaper,buterin2016eip150}; for computationally intensive cryptographic algorithms, Solidity implementations can therefore introduce substantial execution and gas overhead. Alternatively, Ethereum clients can expose selected algorithms as Precompiled Contracts, which execute native client code behind predefined EVM interfaces \cite{evmCodesPrecompiled}. This route improves execution efficiency, but it binds the implementation to the client software. Updating a Precompiled Contract normally requires modifying client source code, rebuilding the client, and coordinating deployment across nodes.

This trade-off leaves a capability gap. Solidity contract implementations provide upgrade flexibility but are not well suited to expensive cryptographic computation. Precompiled Contracts provide native execution efficiency but are difficult to update independently of the client release process. More generally, smart contract engineering already faces persistent challenges around correctness, cost, and maintainability \cite{zou2021smartContracts}. Prior work has examined live-upgradable blockchain clients and automated smart-contract patching \cite{wang2023phoenix,rodler2021evmpatch}, showing the broader relevance of upgradeability in blockchain software. For cryptographic algorithms, however, the challenge is to support algorithm replacement without changing the semantics of historical execution or allowing different nodes to select different algorithm versions at the same block height. A process-local plugin boundary also raises portability and isolation concerns when nodes run on different platforms or local environments. Existing approaches do not directly provide a low-intrusion mechanism for replacing contract-facing cryptographic implementations with a uniform module payload while preserving deterministic activation across nodes.

This paper proposes a general Cryptographic Coprocessor architecture for smart-contract-enabled blockchain clients. The coprocessor decouples the contract-facing cryptographic algorithm interface from the WASM module implementation managed by the client. Smart contracts invoke a stable EVM-facing interface, while the client maintains replaceable WASM algorithm modules behind that interface. The upgrade path combines on-chain coordination with off-chain asynchronous preparation: an upgrade transaction records metadata and emits an event, while client-side listeners verify, compile, and instantiate the target WASM module outside the EVM execution critical path of that transaction. To prevent nodes from switching versions according to local readiness time, the protocol separates asynchronous upgrade preparation from deterministic activation through an Activation Block.

We make three contributions. First, we design a Cryptographic Coprocessor architecture that separates contract-facing cryptographic algorithm interfaces from WASM module implementations, allowing algorithm implementations to be managed and replaced independently of the core EVM execution logic while using a narrower runtime boundary than process-local plugin loading. Second, we design an upgrade protocol that combines on-chain event coordination, off-chain asynchronous WASM preparation, and block-height-based deterministic activation. Third, we implement a prototype in Geth and evaluate it through WASM-based experiments covering upgrade latency in a five-node Clique network and execution efficiency against Precompiled Contract and Solidity contract baselines. The resulting claims are intentionally bounded: the evaluation concerns contract-facing cryptographic algorithms under the evaluated scenarios, does not claim that unrelated EVM transactions are unaffected during the upgrade preparation window, does not set up a separate consistency experiment, and does not treat the WASM sandbox as a formal security proof.

\section{Technical Background}\label{sec2}

\subsection{Cryptographic Execution}\label{sec2.1}
Ethereum smart contracts are programs that run on contract accounts. A contract account is identified by an address, its code hash points to EVM bytecode stored in the state database, and a transaction or message call to that address triggers bytecode execution in the EVM \cite{ethereumSmartContracts,ethereumAccounts,woodEthereumYellowPaper}. Gas is the protocol-level budget for this execution. The protocol charges for opcode execution, memory use, state access, and transaction data, so deterministic execution is coupled to an explicit resource-pricing mechanism \cite{woodEthereumYellowPaper,buterin2016eip150}.

Cryptographic algorithms can be exposed to smart contracts in several ways. A Solidity contract implementation is flexible because it can be deployed and updated at the contract layer, but complex arithmetic or byte-oriented computation is executed as EVM instructions and can therefore incur high latency and gas cost. A Precompiled Contract provides a reserved EVM-facing address whose execution is dispatched to native client code. The elliptic-curve precompiles introduced by EIP-196 and EIP-197, together with EIP-1109's call-cost discussion, illustrate this pattern: the interface is stable at the protocol boundary, while the implementation and gas schedule are fixed by client and protocol rules \cite{eip196,eip197,eip1109,evmCodesPrecompiled}. This improves execution efficiency, but adding or replacing an algorithm usually follows the client release path rather than an application-level deployment path.

\subsection{Runtime Upgrade}\label{sec2.2}
A blockchain client receives and validates blocks, maintains local state, executes transactions, and exposes RPC interfaces. In Ethereum, the execution client handles transaction validation, state management, and EVM execution, while the consensus client handles fork choice and finality coordination \cite{ethereumNodeArchitecture,gethHome}. Updating functionality inside an execution client is therefore different from updating an ordinary application library: a faulty or inconsistently adopted update can affect transaction replayability and the semantics that different nodes apply to the same block.

Traditional client upgrades rely on software distribution, local deployment, and process restart. Dynamic software update (DSU) mechanisms reduce this operational cost in general distributed systems, and live-upgradable blockchain clients show that runtime replacement is also relevant in blockchain software \cite{ajmani2006modular,baresi2017versionConsistency,wang2023phoenix}. For contract-facing cryptographic algorithms, however, runtime upgrade must also preserve a deterministic version boundary. A node must not decide the active cryptographic implementation from local wall-clock time or local preparation completion alone, because the same contract call at the same block height must resolve to the same algorithm version under the same chain view.

\subsection{WebAssembly Runtime}\label{sec2.3}
WebAssembly defines a portable low-level bytecode format intended for compact representation and efficient execution under a host runtime \cite{webassemblyCoreSpec}. A WASM module executes with explicit imports, exports, and linear memory. In this work, WASM is used as the dynamically loaded algorithm artifact, replacing the earlier process-local plugin boundary with a bytecode payload that each node can decode, hash, compile, instantiate, and invoke through a controlled runtime interface.

This runtime boundary is useful for cryptographic algorithm modules because it separates the host client from the module's internal implementation language and binary layout. It also gives the upgrade protocol a concrete artifact, the WASM module bytes and their hash, that can be referenced by on-chain metadata. The boundary is nevertheless an engineering boundary, not a formal proof of sandbox security or cross-platform determinism across all runtimes and compiler toolchains. The evaluation in this paper is limited to the implemented Geth prototype and the evaluated WASM runtime path.

\section{Coprocessor Architecture}\label{sec3}

The Cryptographic Coprocessor is designed to provide runtime-upgradable WASM implementations for contract-facing cryptographic algorithms without turning the entire blockchain client into a dynamically updated component. The scope is deliberately narrow: ordinary transactions continue to execute through the EVM, the execution client continues to charge gas through the EVM call path, and only selected cryptographic algorithm implementations behind a stable contract-facing interface are prepared, loaded, and selected as replaceable WASM modules.

\subsection{System Overview}\label{sec3.1}
Figure~\ref{fig:overview} shows the main modules. The Execution Engine executes ordinary EVM transactions. Identity Hooks recognize calls to the Management Contract entry point used by the prototype and route only those calls into the coprocessor boundary. The Cryptographic Coprocessor manages ABI decoding, algorithm lookup, version selection, gas metadata, and WASM invocation. The Upgrade Handler listens for on-chain upgrade events and prepares node-local artifacts. The WASM Runtime compiles and instantiates modules under a controlled import/export and memory boundary, and WASM Modules contain the replaceable algorithm implementations.

The on-chain layer contains the Management Contract, event log, version metadata, and Activation Block. The Management Contract abstracts the CodeStorage contract used in the prototype: its invocation interface exposes the contract-facing call entry, and its upgrade interface publishes the algorithm name, version, WASM artifact, WASM hash, ABI type metadata, gas value, and activation height. The client-side layer contains the Execution Engine, Identity Hooks, Cryptographic Coprocessor, Upgrade Handler, WASM Runtime, and local module workspace. This split keeps the chain as the authoritative coordination surface while leaving module preparation as node-local work.

\subsection{Invocation Abstraction}\label{sec3.2}
The contract-facing invocation interface is:

\begin{quote}
\texttt{callFunc(string algorithm, bytes input)}
\end{quote}

The \texttt{algorithm} argument names the target cryptographic algorithm, and \texttt{input} carries ABI-encoded parameters. The smart contract does not depend on the location of the compiled artifact, the implementation language, or the local loading state of a node. It depends only on the EVM-visible interface and the ABI-level input-output contract associated with the selected algorithm version.

Inside the client, the coprocessor parses the CodeStorage calldata, normalizes the algorithm name, retrieves the stored metadata, and decodes the input according to the registered type list. It then resolves the implementation for the current block height. Built-in cryptographic routines can be called through the internal registry, while dynamically upgraded algorithms are invoked through the WASM Runtime. After the WASM \texttt{execute} export returns, the coprocessor re-encodes the result according to the registered output type list and returns the bytes to the EVM.

This abstraction decouples contract-facing cryptographic algorithm interfaces from WASM module implementations. Replacing an implementation does not require changing the contract-facing call shape, provided that the registered metadata and ABI-level input-output contract remain compatible. The EVM integration layer also does not need to understand the internal logic of every cryptographic algorithm; it needs a stable dispatch boundary, a gas query, and a deterministic return value for the selected version.

\subsection{Upgrade Protocol}\label{sec3.3}
An upgrade starts from an on-chain proposal. In the versioned path, the proposal is submitted through \texttt{uploadCodeVersion}. The proposal contains the module identifier, module version, encoded WASM bytes, WASM hash, activation height, gas value, and ABI input-output type descriptions. During transaction execution, the Management Contract validates and stores this metadata and emits a versioned upgrade event. The EVM path does not compile or instantiate the WASM module; it records the authoritative metadata and publishes an event that clients can observe.

Each client runs an Event Listener for Management Contract upgrade events. When a listener observes a versioned event, it queries the authoritative metadata from the contract, checks that the event and stored metadata agree on the version and activation height, and delegates preparation to the Upgrade Handler. The Upgrade Handler decodes the uploaded artifact into the local WASM workspace, verifies the artifact hash, asks the WASM Runtime to compile and instantiate the module, checks the required export, and records the resulting artifact as a prepared version.

This workflow separates on-chain coordination from node-local preparation. The chain provides one upgrade proposal and a stable metadata source, while each node independently verifies and prepares the same WASM artifact. A local preparation failure does not roll back the already executed upgrade transaction and must not be interpreted as successful activation. This separation is the basis for asynchronous upgrade preparation and explains why the upgrade transaction itself does not wait for WASM compilation.

\subsection{Deterministic Activation}\label{sec3.4}
Asynchronous preparation creates a consistency problem if nodes switch algorithm versions as soon as their local WASM module is ready. Two nodes may observe the same chain but finish compilation at different physical times. If local readiness determined the active version, the same contract call at the same block height could execute different module implementations. The coprocessor therefore separates preparation time from activation time through an Activation Block.

For module \(m\), execution at block height \(b\) selects the old or new version around activation height \(H_m\) as:

\begin{equation}
V(m,b)=
\begin{cases}
V_{\mathrm{old}}, & b < H_m,\\
V_{\mathrm{new}}, & b \ge H_m.
\end{cases}
\end{equation}

More generally, when multiple versions exist, the version selector chooses the newest prepared version whose Activation Block is not greater than the execution block height. This rule makes activation deterministic with respect to chain height: given the same chain view, metadata, and prepared artifacts, nodes apply the same version-selection rule for the same block. A node that reaches the Activation Block without the required prepared version must not silently fall back to the obsolete implementation for calls requiring the new semantics. In the prototype this is enforced by a required-version check that returns an execution error when the selected version is missing locally.

\subsection{Resource Accounting}\label{sec3.5}
The coprocessor uses deterministic gas accounting rather than CPU-time-based charging. This is necessary because wall-clock execution time differs across machines and cannot be part of consensus-visible execution semantics. A precompile-like gas rule can be expressed as:

\begin{equation}
G_a(x)=G_{\mathrm{base},a}
+\left\lceil\frac{L(x)}{W}\right\rceil G_{\mathrm{unit},a},
\end{equation}

where \(a\) is the algorithm, \(x\) is the ABI-encoded input, \(L(x)\) is the input length, \(W\) is the word size, and \(G_{\mathrm{base},a}\) and \(G_{\mathrm{unit},a}\) are algorithm-specific gas parameters. The prototype records deterministic gas metadata for upgraded algorithms and uses precompile-like pricing functions for native baselines. The evaluation reports \texttt{gasEstimate} under this prototype pricing model; it does not claim that the current parameters are an optimal economic pricing rule for public Ethereum.

\subsection{Prototype Implementation}\label{sec3.6}
We implemented the prototype in Geth by adding the CodeStorage interface, EVM call recognition for the Management Contract entry point, the Cryptographic Coprocessor dispatcher, the activation service, version metadata storage, and the WASM Runtime path. The invocation path recognizes CodeStorage calls, calculates required gas from the registered metadata, decodes the ABI input, selects the applicable algorithm version for the execution block height, invokes the selected WASM module, and returns ABI-encoded output to the EVM.

The upgrade path is event-driven. \texttt{uploadCode} supports the legacy unversioned path, while \texttt{uploadCodeVersion} carries version and activation metadata. The Event Listener observes the emitted upgrade event, and the activation service decodes the uploaded WASM artifact, computes its hash, records runtime metadata, compiles and instantiates the module through the WASM Runtime, and persists the prepared-version metadata. The WASM Runtime uses a memory limit, an execution budget, import validation, and an \texttt{execute} export check. These checks are implementation safeguards for the prototype boundary, not a substitute for a complete production security policy.

\section{Security Analysis}\label{sec4}

\subsection{Threat Model}\label{sec4.1}
The threat model covers risks introduced by dynamic cryptographic algorithm loading. An attacker may submit a malformed or malicious WASM module, provide metadata that does not match the uploaded artifact, attempt to consume excessive CPU, memory, storage, calldata, or block gas, or exploit nodes that prepare an upgrade more slowly than others. The analysis also considers erroneous upgrade artifacts and local preparation failures. We do not model a compromised Geth binary, a broken consensus protocol, or cryptographic primitives whose mathematical security assumptions are false.

\subsection{Execution Isolation}\label{sec4.2}
WASM narrows the execution boundary compared with a process-local plugin or shared-library interface. The module runs inside a WASM Runtime with linear memory, explicit exports, and validated imports. In the prototype, modules are invoked through a fixed \texttt{execute} export, and imported memories or unauthorized host imports are rejected. This design reduces direct access from the algorithm module to Geth process memory, local files, system networking, and host functions that are not explicitly exposed.

The isolation claim is intentionally bounded. WASM sandboxing reduces the trusted boundary of dynamically loaded algorithm code, but it is not presented here as a formal proof of security for all runtimes, compiler toolchains, or host configurations. A production deployment would need additional hardening, including stronger artifact admission policies, runtime diversity testing, reproducible builds, and governance rules for approving cryptographic modules.

\subsection{Resource Abuse}\label{sec4.3}
Dynamic algorithm loading creates resource-abuse risks. A module may be large, slow to compile, memory intensive, or designed to run for a long time. A low gas setting could underprice an expensive cryptographic operation, causing denial-of-service (DoS) pressure on the execution client. Large uploaded artifacts may also increase calldata, storage, propagation, and data-availability pressure.

The design addresses these risks by keeping gas accounting deterministic, bounding module memory, applying an execution budget, validating imports and required exports, and separating module preparation from the upgrade transaction's EVM execution path. These measures reduce the immediate attack surface, but they do not fully solve economic pricing. The current prototype gas values are experimental parameters, and future work must calibrate gas pricing against execution cost, storage cost, calldata cost, and data availability cost.

\subsection{Upgrade Consistency}\label{sec4.4}
Upgrade consistency is treated as a security property of the protocol. The WASM hash identifies the artifact, on-chain metadata identifies the target version and activation height, and the Activation Block defines the common version-switching boundary. Because local wall-clock time and local readiness time are not used for version selection, nodes with the same chain view use the same version rule for a given block height.

This paper does not set up a separate consistency experiment. The consistency discussion therefore remains a protocol analysis: deterministic activation defines the intended version boundary, but it is not reported here as node-level evidence for state-root equality, arbitrary network safety, or fail-stop behavior under injected unprepared-node failures. The design requirement remains that an unprepared node must reject the required new-version execution rather than silently continue with the obsolete implementation.

\section{Evaluation}\label{sec5}

The evaluation asks whether the proposed coprocessor can be used as a practical execution path for upgradable contract-facing cryptographic algorithms. Following the target outline, we focus on upgrade efficiency and execution efficiency. Upgrade consistency is discussed as a protocol security property in Section~\ref{sec4.4} and is not set up as a separate experiment.

\subsection{Experimental Setup}\label{sec5.1}
The experiments were run on a Geth-based private chain on Ubuntu 24.04. For the multi-node experiments, we used a five-node Clique network with one signer and four observer nodes, a block period of 5 s, and network identifier 11223344. The current experiment ledger does not record the host CPU, memory, storage device, or exact prototype commit; these metadata remain TODO for reproducibility reporting. Although 2-node and 10-node network configurations exist in the repository, the formal paper data used here come from the five-node setting and should not be described as a completed scale-out comparison.

The evaluation covers seven algorithms: Add, Sha256, Blake2bSum256, Pbkdf2Sha256, Dh2048Secret, PedersenCommit, and SchnorrVerify. Add is a non-cryptographic baseline, whereas the remaining algorithms exercise hash functions, password-based key derivation, key exchange, commitments, and signature verification. For upgrade efficiency, a node is counted as complete only when its RPC endpoint returns the expected output from \texttt{CodeStorage.callFunc}. For execution efficiency, we compare three paths after setup has completed: WASM-backed Upgrade through CodeStorage, client-native Precompile, and Solidity Contract. We report \texttt{eth\_call} latency and \texttt{gasEstimate}; \texttt{gasEstimate} is obtained from \texttt{eth\_estimateGas} and is not receipt \texttt{gasUsed}.

\subsection{Upgrade Efficiency}\label{sec5.2}
The upgrade-efficiency experiment measured the control-plane time from submitting a WASM upgrade transaction to the point at which all five target nodes could call the uploaded algorithm successfully. The measured timeline included transaction hash observation, sender receipt observation, receipt-derived event observation, node-level \texttt{callFunc} completion, and all-node completion. It is intentionally end-to-end and externally observable, including RPC round trips and polling intervals; it should not be read as a precise decomposition of internal WASM compilation time.

Figure~\ref{fig:wasm-evaluation}a shows the latency breakdown for the seven algorithms in the WASM rerun reported here. Across the five-node Clique experiments, the total submit-to-all-complete latency ranged from 4.857 s for Pbkdf2Sha256 to 5.342 s for SchnorrVerify, with a mean of 5.022 s. The sender observed a successful transaction receipt after roughly one 5 s block interval, whereas the post-event readiness tail ranged from 3.258 ms for Add to 287.298 ms for SchnorrVerify. These results support the intended separation between on-chain upgrade publication and node-local preparation. The upgrade transaction completed before all nodes became callable, indicating that WASM artifact verification, compilation, export checking, and instantiation were outside the EVM execution path of that transaction.

We also measured the upload cost of the event-bearing upgrade transaction and compared it with Solidity contract deployment for Add and Blake2bSum256 (Figure~\ref{fig:lab1-deployment-cost}). This auxiliary experiment measures total transaction-level setup cost; it does not isolate event-log gas from storage and calldata costs. For Add, the upgrade upload used 85,612 gas, compared with 60,918 gas for the minimal Solidity deployment, and the mean receipt latency was 1.71 s versus 1.01 s. For Blake2bSum256, the upgrade upload used 87,180 gas, whereas the Solidity deployment used 852,059 gas; the corresponding mean receipt latencies were 1.71 s and 1.01 s. Precompiled Contracts have no deployment transaction in this comparison because they are already built into the client. Because this auxiliary cost experiment covers only Add and Blake2bSum256, we do not generalize the deployment-cost trend to all algorithms.

The present upgrade-efficiency experiment does not measure the latency, throughput, transaction success rate, or longest block interval of unrelated EVM transactions during the preparation window. Those availability-oriented measurements require a concurrent workload between receipt observation and all-node callable completion and are left for future work.

\subsection{Execution Efficiency}\label{sec5.3}
The execution-efficiency experiment evaluated whether the WASM-backed dynamic upgrade mechanism adds substantial overhead after an algorithm has already been prepared. Each algorithm was measured with 10 warm-up calls and 100 formal \texttt{eth\_call} samples for each implementation path. The comparison therefore concerns steady-state invocation cost, not setup or upload latency.

Figure~\ref{fig:wasm-evaluation}b compares mean \texttt{eth\_call} latency across Upgrade, Precompile, and Contract paths. The WASM-backed Upgrade path remained in the same millisecond-scale range as the Precompile path for six of the seven evaluated algorithms: Add, Sha256, Blake2bSum256, Pbkdf2Sha256, Dh2048Secret, and PedersenCommit ranged from 1.002 to 1.876 ms through Upgrade, compared with 0.868 to 1.013 ms through Precompile for the corresponding cases. The same data also expose an important limitation: SchnorrVerify took 188.600 ms through Upgrade, compared with 1.946 ms through Precompile and 6.425 ms through Contract. These observations support the main performance claim only in a bounded form: dynamically loaded WASM algorithms retain performance comparable to Precompiled Contracts for most evaluated benchmarks, but the SchnorrVerify tail shows that module implementation and runtime behavior can dominate the invocation cost.

Figure~\ref{fig:wasm-evaluation}c reports \texttt{gasEstimate} for the same calls. Upgrade and Precompile had similar gas estimates under the prototype pricing model for the evaluated WASM and Precompile paths. For Sha256, the estimates were 25,801 gas for Upgrade and 25,156 gas for Precompile; for Blake2bSum256, the same two values were observed. For complex Solidity implementations, the Contract path incurred substantially larger estimates: PedersenCommit required 853,145 gas compared with 225,695 gas for Upgrade, and SchnorrVerify required 2,301,691 gas compared with 229,437 gas for Upgrade. These gas numbers should be interpreted only as the current prototype's pricing results from \texttt{eth\_estimateGas}. They do not prove that the proposed architecture has inherently lower economic cost than official Ethereum precompile pricing, and they are not receipt-level \texttt{gasUsed} measurements.

\section{Related Work}\label{sec6}

This work is related to EVM cryptographic extension mechanisms, blockchain runtime upgrades, and WASM execution in blockchain systems. We organize prior work by mechanism, because the main distinction is where the upgrade boundary is placed and how deterministic execution is preserved.

\subsection{EVM Cryptographic Extensions}\label{sec6.1}
Ethereum's EVM provides a deterministic bytecode execution environment for smart contracts, and gas prices the resources consumed by this execution \cite{woodEthereumYellowPaper,ethereumEVM}. Contract-level cryptographic implementations inherit the deployability of Solidity but also inherit EVM instruction-level overhead. Precompiled Contracts expose selected native routines through reserved EVM-facing addresses, giving smart contracts access to efficient client-side implementations for specific algorithms \cite{evmCodesPrecompiled,eip196,eip197}. Existing precompiles therefore demonstrate the value of native cryptographic execution, but they also illustrate the rigidity of tying algorithm availability and pricing to client and protocol changes.

The Cryptographic Coprocessor targets this gap. It does not replace existing precompiles or change the semantics of ordinary EVM bytecode execution. Instead, it introduces a controlled client-side boundary for contract-facing cryptographic algorithms whose implementations are supplied as WASM modules and selected by version metadata.

\subsection{Blockchain Runtime Upgrades}\label{sec6.2}
General DSU research studies how running systems can change components while preserving service continuity. KylinX uses dynamic library operating-system techniques for runtime library replacement, Mvedsua combines dynamic update with multi-version execution, PYLIVE supports on-the-fly code changes for Python services, and distributed update work has studied modular upgrades and version consistency across components \cite{zhang2018kylinx,pina2019mvedsua,huang2021pylive,ajmani2006modular,baresi2017versionConsistency}. These systems provide useful concepts, but they do not directly address the blockchain requirement that independently executing nodes must choose the same semantics for the same block height.

Blockchain-specific upgrade mechanisms add this determinism requirement. Cardano's hard-fork-combinator documentation describes protocol-era transitions at designated upgrade points \cite{cardanoHardForkCombinator,cardanoEvolution}. Updatable-blockchain work studies synchronization across old and new chains \cite{ciampi2020updatable}. Zindros examines soft-fork-based policy upgrades \cite{zindros2021softPower}. Phoenix embeds upgrade code in blockchain transactions for a live-upgradable blockchain client \cite{wang2023phoenix}. EVMPatch automatically patches deployed smart contracts through bytecode rewriting and proxy-based deployment \cite{rodler2021evmpatch}. These mechanisms cover protocol upgrades, client-wide upgrade, policy update, and contract patching. The coprocessor is narrower: it upgrades contract-facing cryptographic algorithm implementations behind a stable EVM-facing interface.

\subsection{WebAssembly Execution}\label{sec6.3}
WASM has become an attractive execution substrate for blockchain systems because it provides a portable bytecode format, explicit host interfaces, and efficient runtime execution \cite{webassemblyCoreSpec}. Polkadot uses a WASM-based runtime upgrade path in which chain logic can be stored and updated through on-chain governance \cite{polkadotRuntimeUpgrades}. That approach shows the usefulness of WASM for upgradeable blockchain execution, but its scope is broad runtime logic rather than a specific class of EVM-facing cryptographic functions.

The coprocessor uses WASM at a smaller boundary. A WASM module represents a cryptographic algorithm implementation, while the EVM-facing call shape and chain-level version-selection rule remain stable. This gives the prototype a uniform module payload and a controlled runtime boundary, but it does not by itself prove cross-platform determinism or sandbox security for every runtime. Those properties remain engineering and governance concerns for future deployments.

\section{Conclusion}\label{sec7}

This paper presented an upgradable Cryptographic Coprocessor for the EVM. The central contribution is to separate a stable contract-facing invocation interface from client-side WASM module implementations, so that cryptographic algorithms can be managed as replaceable modules while ordinary EVM execution remains outside the upgrade mechanism. The upgrade protocol combines on-chain proposals, off-chain asynchronous WASM preparation, and Activation-Block-based deterministic activation.

The Geth prototype and WASM rerun support the design under the evaluated private-chain scenarios. The five-node upgrade experiments showed that upgrade publication and local WASM preparation are separated: the upgrade transaction recorded metadata and emitted an event before all nodes became callable. The execution-efficiency experiment showed that dynamically loaded WASM algorithms remained close to Precompiled Contract execution for most evaluated algorithms, while SchnorrVerify exposed a clear tail-latency limitation. Upgrade consistency remains a protocol property discussed through the Activation Block design rather than a separate experiment.

The current result has clear boundaries. It does not prove zero-downtime service availability, universal cross-platform determinism, WASM sandbox security, fail-stop behavior under injected unprepared-node failures, state-root equality during upgrades, or consensus safety for arbitrary network sizes. Future work should calibrate the gas pricing mechanism, harden the upgrade channel against DoS and data-availability saturation attacks, define stricter ABI-version compatibility rules, validate additional cryptographic algorithms and WASM toolchains, and design separate consistency and fail-stop evaluations if those properties are later claimed experimentally.
