\begin{abstract}
Smart contracts frequently rely on cryptographic algorithms, yet implementing complex cryptographic computation in Solidity expands it into large sequences of EVM instructions, resulting in substantial execution overhead and gas consumption. Precompiled Contracts reduce these costs by exposing client-side routines at fixed addresses, but they provide no runtime mechanism for evolving an algorithm independently of client releases and coordinated network upgrades. We present EvoCrypt, an upgradeable cryptographic coprocessor framework  that exposes a stable contract-facing interface while executing replaceable WebAssembly (WASM) modules in a controlled client-side runtime. EvoCrypt distributes version metadata on-chain and deterministically activates an installed module at a designated block height, allowing participating nodes to switch algorithm versions consistently. Each invocation is charged according to a deterministic algorithm-level gas schedule associated with the activated version, thereby avoiding the cost of expanding the algorithm into EVM instructions while retaining explicit resource accounting. We implement EvoCrypt in Geth and evaluate it on a 20-node private network. The experiments show that EvoCrypt improves the efficiency of contract-facing cryptographic upgrades and invocations compared with Solidity-based implementations, while retaining near-Precompiled-Contract execution costs for most benchmark algorithms. EvoCrypt also supports the deployment of complex cryptographic algorithms that are difficult to realize directly in the EVM ecosystem.

\keywords{blockchain \and smart contracts \and upgrade \and WebAssembly}
\end{abstract}

\section{Introduction}\label{sec1}

As blockchain systems become programmable platforms, smart contracts increasingly depend on cryptographic algorithms for authentication, integrity, signatures, and privacy \cite{nakamoto2008bitcoin,zou2021smartContracts,woodEthereumYellowPaper,ethereumEVM}. The long-term security of these applications also requires the ability to adopt new algorithms, including post-quantum alternatives, without disrupting contract-facing functionality \cite{shor1999,grover1996,nistPqcProject}. Blockchain clients therefore need an extensible way to provide evolving cryptographic capabilities to smart contracts.

Ethereum provides two main mechanisms for executing cryptographic operations: Solidity contract implementations and Precompiled Contracts. Solidity implementations are flexible and deployable at the contract layer, but complex cryptographic computation expands into costly EVM execution; Precompiled Contracts execute selected routines efficiently in client-side code, but their supported algorithms are fixed to the client and normally require coordinated client updates to change \cite{woodEthereumYellowPaper,ethereumEVM,evmCodesPrecompiled}.

Together, these mechanisms expose a fundamental trade-off between execution efficiency and algorithm upgradability. Solidity keeps algorithms deployable without client changes but can impose substantial execution and gas overhead, whereas Precompiled Contracts provide efficient execution only for routines embedded in the client and are therefore difficult to evolve independently. The central challenge is to replace contract-facing cryptographic implementations without sacrificing efficient execution, deterministic behavior across nodes, or compatibility with the existing EVM interface.

EvoCrypt addresses this trade-off by separating the stable contract-facing interface from replaceable WASM implementations and by separating module preparation from module activation. The interface preserves how smart contracts invoke cryptographic operations, while portable WASM modules allow implementations to be replaced without embedding each algorithm in contract bytecode or rebuilding the client for every change. Asynchronous preparation moves verification, compilation, and instantiation away from the transaction execution path. Activation-Block-based selection then ensures that nodes switch versions according to a common chain-derived rule rather than local readiness time. The design combines algorithm-level accounting with deterministic, incrementally deployable upgrades.

The main contributions of this article are summarized as follows.
\begin{itemize}
    \item First, we design an upgradeable cryptographic coprocessor that separates the stable contract-facing interface from replaceable WASM-based algorithm implementations, allowing complex cryptographic operations to execute outside the EVM while preserving contract compatibility.
    \item Second, we design an activation-block-based upgrade protocol in which upgrade proposals are published on-chain, ensuring that clients derive the same proposal from a common authoritative record. By distributing and verifying a uniform WASM bytecode artifact, the protocol further ensures consistent module execution across clients when the upgrade becomes active.
    \item Finally, we implement EvoCrypt in Geth and evaluate it on a 20-node private blockchain network. The results show that EvoCrypt reduces the implementation burden and calling cost of the evaluated cryptographic operations while supporting dynamic evolution of contract-facing algorithms.
\end{itemize}

\section{Related Work}\label{sec2}

Blockchain upgrades at the protocol or client layer replace execution rules through a coordinated transition. Cardano switches protocol eras with a hard-fork combinator at designated heights, and work on updatable blockchains studies how old and new chains stay synchronized \cite{cardanoHardForkCombinator,cardanoEvolution,ciampi2020updatable}. Soft forks instead encode selected policy changes in rules that can be adopted without replacing the protocol \cite{zindros2021softPower}. Phoenix and Polkadot are closest to EvoCrypt in supporting live replacement: Phoenix carries upgrade code in transactions and compiles it at runtime, while Polkadot stores governance-approved WASM as on-chain runtime logic and replaces the state-transition function during block synchronization \cite{wang2023phoenix,polkadotRuntimeUpgrades}. Both nevertheless replace client or chain-runtime components rather than a contract-facing cryptographic algorithm. They do not specify how a contract names an algorithm, binds a compatible input-output interface, pays an invocation fee, and switches versions at a block height without redeploying the caller. EvoCrypt narrows the replacement boundary to individual WASM modules behind a stable Solidity-facing interface, with consistency derived from hash-identified metadata, activation height, and per-algorithm resource parameters.

Contract-level schemes update application logic through deployable contracts, proxy indirection, or bytecode rewriting. EVMPatch patches deployed Ethereum contracts via rewriting and proxy deployment \cite{rodler2021evmpatch,ethereumEVM}; LEAGAN adds data separation, incremental hashing, and status-contract versioning \cite{kumar2025leagan}. Solidity implementations remain constrained by EVM cost and interface compatibility, whereas replacing a Precompiled Contract normally requires client and protocol changes \cite{evmCodesPrecompiled,eip196,eip197}. Below the application layer, dynamic software updates load new components into a running host. KylinX supports runtime library replacement, Mvedsua combines updates with multi-version execution, PYLIVE changes Python code online, and distributed-system work addresses modular updates and version consistency \cite{zhang2018kylinx,pina2019mvedsua,huang2021pylive,ajmani2006modular,baresi2017versionConsistency}. WASM provides a portable artifact and an explicit host boundary for this style of replacement \cite{webassemblyCoreSpec}, but existing blockchain uses of WASM generally target whole-runtime logic rather than a narrow EVM-facing cryptographic interface.


\section{EvoCrypt Design}\label{sec3}

EvoCrypt is a cryptographic coprocessor framework for dynamically upgrading contract-facing cryptographic algorithms. This section presents the system model, the upgrade protocol, and the invocation protocol that together define the design. We focus on the coordination, version-selection, and contract-facing execution rules of EvoCrypt, while the prototype implementation and experimental configuration are described in Section~\ref{sec5}.

\subsection{System Model}\label{sec3.1}
EvoCrypt separates governance, chain state, contract execution, and module execution into four cooperating components: the Community, the Blockchain, the EVM, and the Cryptographic Coprocessor. The Community includes developers and an authorizing committee that proposes and approves algorithm upgrades. The Blockchain maintains the canonical chain and shared world state, including smart contracts and the Management Contract. The EVM processes smart-contract transactions, while the node-local Cryptographic Coprocessor prepares, activates, and executes replaceable cryptographic modules.

Two chain-derived paths connect these components. An approved proposer records an upgrade through the Management Contract, whereas a contract initiates an invocation through the EVM of a Blockchain node. The Management Contract stores algorithm metadata and exposes the contract-facing upgrade and invocation interfaces. The coprocessor uses the resulting chain state to prepare and execute the corresponding module. Figure~\ref{fig:overview} summarizes these objects and their relationships.

\subsection{Upgrade Protocol}\label{sec3.2}
\noindent\textbf{On-chain publication.} On-chain publication provides the authoritative record that coordinates node-local preparation and height-based activation. After the committee approves a proposal, a committee-authorized proposer submits it through the designated upgrade interface. The Management Contract admits the proposal only after the committee has reached consensus on its contents, stores the version metadata, and emits an upgrade event.

The EVM records metadata but does not compile or instantiate the WASM module. Node-dependent preparation therefore remains outside the transaction that changes the chain state. Every node reconstructs the same version from the admitted record, which identifies the algorithm, version, WASM artifact, module hash, interface descriptors, resource parameters, and Activation Block. Only $\langle a,v,H_{a,v}\rangle$ is emitted as a notification index. Let $\mathcal{V}_{a}$ denote the versions already registered for algorithm $a$; the authoritative record prevents nodes from preparing different artifacts or execution rules for the same upgrade.

\begin{definition}[Version metadata]
\label{def:version-metadata}
Let $a$ be an algorithm name and $v$ a version number. An admitted upgrade is the metadata record
\begin{equation}
\mu_{a,v}=\bigl(a,\,v,\,C_{a,v},\,h_{a,v},\,g^{(0)}_{a,v},\,\lambda_{a,v},\,\tau^{\mathrm{in}}_{a,v},\,\tau^{\mathrm{out}}_{a,v},\,H_{a,v}\bigr),
\label{eq:version-metadata}
\end{equation}
where $C_{a,v}$ is the compiled WASM bytecode, $h_{a,v}=\mathrm{Keccak256}(C_{a,v})$ is the module hash, $g^{(0)}_{a,v}$ is the initial gas fee, $\lambda_{a,v}$ is the gas slope parameter, $\tau^{\mathrm{in}}_{a,v}$ and $\tau^{\mathrm{out}}_{a,v}$ are the ABI input and output type descriptors, and $H_{a,v}$ is the Activation Block height. The Management Contract stores an encoding of these fields. Each node recomputes $h_{a,v}$ from the recovered bytecode during preparation and binds that hash to the prepared version.
\end{definition}

\noindent\textbf{Node-local preparation.} Node-local preparation converts the admitted metadata record into executable state without changing the active version. After observing the upgrade event, each client recovers $\mu_{a,v}$, checks that the event index agrees with the stored record, decodes the artifact, and recomputes its hash. The Upgrade Handler then compiles and instantiates the module and validates its required entry point. Once these checks succeed, the node records $(a,v)$ as prepared. Algorithm~\ref{alg:upgrade-protocol} gives the complete publication and preparation procedure.

Preparation is deliberately separated from the chain-level upgrade record. Node-local work can proceed asynchronously, failed attempts can retry from the authoritative chain record, and an executed upgrade transaction is not rolled back. The separation allows preparation to complete without changing the version selected by the chain.

\centering
\includegraphics[width=0.84\textwidth]{../image/upgrade_protocol.pdf}
\caption{Node-local preparation and deterministic activation of an EvoCrypt upgrade.}
\label{fig:upgrade-protocol}

\begin{algorithm}[!htb]
\caption{\textbf{Activation-Block-based WASM upgrade protocol.}}
\label{alg:upgrade-protocol}
\begin{algorithmic}[1]
\Require Metadata $\mu_{a,v}$ as in~\eqref{eq:version-metadata}; node set $\mathcal{N}$
\Ensure Prepared set updated on every $n_i\in\mathcal{N}$
\State committee-authorized proposer submits $\mu_{a,v}$ through the designated upgrade interface
\State Management Contract stores $\mu_{a,v}$; emits event $\langle a,v,H_{a,v}\rangle$
\ForAll{$n_i\in\mathcal{N}$}
    \State observe $\langle a,v,H_{a,v}\rangle$; fetch $\mu'_{a,v}$ from Management Contract
    \If{event fields disagree with $\mu'_{a,v}$}
        \State reject $(a,v)$
    \Else
        \State decode $\widehat{C}$ from $\mu'_{a,v}$; reject $(a,v)$ unless $\mathrm{Keccak256}(\widehat{C})=h_{a,v}$\label{line:hash-check}
        \Repeat
        \State compile and instantiate $\widehat{C}$; validate the required module entry point
        \Until{preparation succeeds}
        \State persist $\widehat{C}$ under $h_{a,v}$ with $\mu_{a,v}$; mark $(a,v)$ prepared\label{line:mark-prepared}
    \EndIf
\EndFor
\end{algorithmic}
\end{algorithm}

\noindent\textbf{Height-based activation.} Height-based activation makes the selected version a function of shared chain height rather than node-local preparation time. The Upgrade Block includes the admitted upgrade transaction and emits $\langle a,v,H_{a,v}\rangle$. After that block, each node independently completes the off-chain Load--Verify--Ready sequence, while invocations before $H_{a,v}$ continue to use the previously selected version. At the Activation Block, nodes with the same chain view select version $v$ according to the rule below. Compilation-time differences therefore cannot change the version selected at a given execution height.

When a selected version is not yet prepared, the node reloads its authoritative metadata and continues preparation rather than selecting an obsolete version. The policy preserves height-based selection while allowing node-local readiness to complete asynchronously. Figure~\ref{fig:upgrade-protocol} shows the separation between publication, preparation, and activation.

\begin{definition}[Active version]
\label{def:active-version}
Let $\mathcal{V}_{a}$ be the registered version set of algorithm $a$, and let $b$ be the execution block height. The version used at height $b$ is
\begin{equation}
v^{*}(a,b)=
\underset{v \in \mathcal{V}_{a}}{\arg\max}
\left\{
\left(H_{a,v},\,v\right)
\;\middle|\;
H_{a,v} \leq b
\right\}.
\label{eq:version-select}
\end{equation}
The $\arg\max$ is lexicographic on the pair $(H_{a,v},v)$: among versions whose activation height does not exceed $b$, the rule prefers the latest activation height and, for a tied height, the larger version number. If the feasible set is empty, no version is active and the invocation fails with a missing-version error.
\end{definition}

\subsection{Invocation Protocol}\label{sec3.3}
A unified Management Contract entry point keeps the contract-facing call boundary stable. The caller serializes the algorithm name $a$ and its parameters into an encoded request $x$ and submits it through the designated interface, so different algorithms share one destination address and the contract binds to the ABI descriptors of the selected version rather than to module location, implementation language, or node-local loading state. EVM-side Hooks admit only requests to that interface; all others remain on the ordinary EVM path. For a routed request the coprocessor parses $(a,x)$, resolves $v^{*}(a,b)$ by~\eqref{eq:version-select}, and, under the mandatory-preparation policy, prepares the selected version if necessary rather than falling back to an obsolete implementation. The selected module receives the encoded parameters and returns an encoded result; the call shape remains compatible when $\tau^{\mathrm{in}}_{a,v}$ and $\tau^{\mathrm{out}}_{a,v}$ are compatible. Algorithm~\ref{alg:invocation-protocol} specifies this procedure and its protocol-error conditions.

\begin{definition}[Algorithm-level gas schedule]
\label{def:gas-schedule}
Each algorithm version uses an independent deterministic pricing rule. A call with inner input $x$ against version $v$ of algorithm $a$ is charged
\begin{equation}
G(a,v,x)=g^{(0)}_{a,v}+\lambda_{a,v}\cdot |x|,
\label{eq:gas-price}
\end{equation}
where $|x|$ is the byte length of the call-stage inner input, $g^{(0)}_{a,v}$ is the initial gas fee, and $\lambda_{a,v}$ is the gas slope parameter registered in $\mu_{a,v}$.
\end{definition}

\begin{algorithm}[!htb]
\caption{\textbf{Contract-to-coprocessor invocation protocol.}}
\label{alg:invocation-protocol}
\begin{algorithmic}[1]
\Require Recognized invocation request $d$, block height $b$, gas budget $g$
\Ensure ABI-encoded result $y$ or explicit error
\State $(a,x)\gets\mathrm{Parse}(d)$
\If{the request is invalid}
    \State \textbf{return} ABI error
\EndIf
\State $v\gets v^{*}(a,b)$ by~\eqref{eq:version-select}\label{line:resolve}
\If{no applicable version exists}
    \State \textbf{return} missing-version error\label{line:missing}
\EndIf
\State ensure $(a,v)$ is prepared under the mandatory-preparation policy\label{line:ensure}
\State $G_{\mathrm{req}}\gets G(a,v,x)$ by~\eqref{eq:gas-price}
\If{$g<G_{\mathrm{req}}$}
    \State \textbf{return} out-of-gas error
\EndIf
\State charge $G_{\mathrm{req}}$; $y\gets\mathrm{Execute}(a,v,x)$\label{line:execute}
\State \textbf{return} $y$, or runtime error on failure
\end{algorithmic}
\end{algorithm}

Because $G$ depends only on registry coefficients and $|x|$, every node that resolves the same $v^{*}(a,b)$ and receives the same input charges an identical fee, independently of local CPU time or WASM instruction counts. Coefficients used in Section~\ref{sec5} demonstrate the pricing mechanism rather than a calibrated economic optimum.

\section{Security Analysis}\label{sec4}

This section formalizes the upgrade protocol and derives the invocation guarantees from it. Section~\ref{sec4.1} fixes the ledger and registry abstractions, the trusted assumptions, the adversary, and game-based definitions for the two failure modes an upgrade mechanism must exclude: honest nodes selecting different versions for the same height, and an honest node executing bytecode other than the admitted artifact. Section~\ref{sec4.2} shows that EvoCrypt excludes the first unconditionally relative to the ledger abstraction and the second by a tight reduction to the collision resistance of $\mathrm{Keccak256}$, and combines both into an upgrade-soundness theorem. Section~\ref{sec4.3} extends consistency to invocation outcomes, and Section~\ref{sec4.4} treats the residual risks the model leaves open and the governed recovery path that addresses them.

\subsection{Security Model}\label{sec4.1}

\noindent\textbf{Notation and ledger.} $\kappa$ is the security parameter, $\mathsf{negl}(\kappa)$ a negligible function, and algorithms are probabilistic polynomial time (PPT) unless stated otherwise. $\mathcal{N}$ is the set of honest nodes, each running Algorithms~\ref{alg:upgrade-protocol} and~\ref{alg:invocation-protocol}. The symbols $\mu_{a,v}$, $C_{a,v}$, $h_{a,v}$ and $H_{a,v}$ are as in Definition~\ref{def:version-metadata}, and $u_{a,v}$ denotes the height of the Upgrade Block that admitted $\mu_{a,v}$. We abstract the blockchain as a transaction ledger: honest node $n$ holds a local view $\mathcal{L}_n$, a finite block sequence with prefix $\mathcal{L}_n[1..b]$ and height $|\mathcal{L}_n|$. Transaction order inside a block is part of the ledger, so an execution point is a height together with a position in the block; we write $b$ for both.

\begin{definition}[Registry state]
\label{def:registry}
The registry $\mathsf{Reg}(P)$ of a ledger prefix $P$ is the Management Contract storage obtained by executing $P$ from the genesis state; by EVM determinism it is a function of $P$. For a node $n$ and height $b$, let $\mathcal{V}^{n}_{a}(b)=\{v \mid \mu_{a,v}\in\mathsf{Reg}(\mathcal{L}_n[1..b])\}$ and let $v^{*}_{n}(a,b)$ be the value of~\eqref{eq:version-select} over $\mathcal{V}^{n}_{a}(b)$, with $v^{*}_{n}(a,b)=\bot$ when the feasible set is empty.
\end{definition}

\noindent\textbf{Trusted assumptions.} Assumptions~\ref{asm:ledger}--\ref{asm:cr} are used in Section~\ref{sec4.2}; Assumption~\ref{asm:runtime} only in Section~\ref{sec4.3}.

\begin{assumption}[Canonical ledger]
\label{asm:ledger}
For all honest $n,n'\in\mathcal{N}$ and every $b\le\min(|\mathcal{L}_n|,|\mathcal{L}_{n'}|)$, $\mathcal{L}_n[1..b]=\mathcal{L}_{n'}[1..b]$.
\end{assumption}

This is the persistence property of a robust transaction ledger~\cite{garay2015backbone}, applied to the prefixes at which invocations are evaluated; blocks still subject to reorganization are re-executed by the ordinary EVM rules and lie outside the model.

\begin{assumption}[Committee-gated admission]
\label{asm:committee}
The Management Contract admits $\mu_{a,v}$ only on a committee-authorized submission, and every admitted record is well formed: (i) $h_{a,v}=\mathrm{Keccak256}(C_{a,v})$; (ii) $u_{a,v}<H_{a,v}$, i.e., the record is committed strictly before its Activation Block; (iii) $(a,v)$ is unique, and an admitted record is never modified or removed; (iv) $C_{a,v}$ passes validation of the configured WASM Runtime. The committee is further trusted to review the implementation and its gas schedule before admission. Conditions (i)--(iii) can be enforced by the contract itself; listing them as assumptions keeps the analysis independent of the contract implementation.
\end{assumption}

\begin{assumption}[Collision resistance]
\label{asm:cr}
For every PPT algorithm $\mathcal{B}$,
\begin{equation}
\begin{split}
\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B})
=\Pr\bigl[&(C,C')\leftarrow\mathcal{B}(1^{\kappa}) :\\
&C\neq C' \wedge \mathrm{Keccak256}(C)=\mathrm{Keccak256}(C')\bigr]
\le\mathsf{negl}(\kappa).
\end{split}
\label{eq:cr-adv}
\end{equation}
\end{assumption}

$\mathrm{Keccak256}$ is unkeyed, so~\eqref{eq:cr-adv} is read in the concrete sense of Rogaway~\cite{rogaway2006ignorance}: each reduction below exhibits an explicit collision finder $\mathcal{B}$ and bounds the protocol adversary's advantage by that of $\mathcal{B}$.

\begin{assumption}[Deterministic runtime]
\label{asm:runtime}
The WASM Runtime exposes a validation predicate $\mathsf{Validate}(C)\in\{0,1\}$ and an execution function $\mathsf{Exec}(C,x)$ whose outputs, including error outcomes, depend only on $(C,x)$ and the fixed, allowlisted host interface. It enforces bounded linear memory, import validation and the configured resource limits, and exposes no host state or capability beyond that interface.
\end{assumption}

\noindent\textbf{Adversary.} The PPT adversary $\mathcal{A}$ may (a) submit arbitrary transactions, including invocation inputs and candidate upgrade proposals, the latter admitted only subject to Assumption~\ref{asm:committee}; (b) schedule the delivery of upgrade events, delay or interrupt node-local preparation, and crash and restart nodes so that preparation retries; and (c) tamper with the node-local artifact path, i.e., replace the byte sequence $\widehat{C}$ that a node obtains when it decodes, persists or reloads an artifact, modelling corrupted caches, persisted copies and untrusted retrieval channels. It cannot violate Assumptions~\ref{asm:ledger}--\ref{asm:cr}, forge committee authorization, or alter the client binary. The model thus excludes a compromised Geth binary, a broken consensus protocol, a captured committee, a failed implementation review, and a primitive whose underlying assumption is false.

\noindent\textbf{Security definitions.} Each experiment below runs $\mathcal{A}$ against the honest nodes in this model and outputs $1$ when $\mathcal{A}$ causes the undesirable event; the advantage of $\mathcal{A}$ is the probability of output $1$ over all coins.

\begin{definition}[Version divergence]
\label{def:div}
In $\mathsf{Exp}^{\mathrm{div}}_{\mathcal{A}}(\kappa)$, the adversary finally outputs a tuple $(a,b,n,n')$ with $n,n'\in\mathcal{N}$ and $b\le\min(|\mathcal{L}_n|,|\mathcal{L}_{n'}|)$. The experiment outputs $1$ iff $v^{*}_{n}(a,b)\neq v^{*}_{n'}(a,b)$, where $\bot$ differs from every version. $\mathsf{Adv}^{\mathrm{div}}_{\mathcal{A}}(\kappa)=\Pr[\mathsf{Exp}^{\mathrm{div}}_{\mathcal{A}}(\kappa)=1]$.
\end{definition}

\begin{definition}[Module substitution]
\label{def:sub}
$\mathsf{Exp}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)$ outputs $1$ iff some honest node $n$ marks $(a,v)$ as prepared with, or executes for $(a,v)$, a byte sequence $\widehat{C}$ such that $\mu_{a,v}\in\mathsf{Reg}(\mathcal{L}_n)$ and $\widehat{C}\neq C_{a,v}$. $\mathsf{Adv}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)=\Pr[\mathsf{Exp}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)=1]$.
\end{definition}

\begin{definition}[Upgrade soundness]
\label{def:sound}
$\mathsf{Exp}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)$ outputs $1$ iff some honest node executes an invocation of $a$ at height $b$ with a byte sequence $\widehat{C}\neq C_{a,v^{*}(a,b)}$, where $v^{*}(a,b)$ is evaluated on the canonical prefix of height $b$; executing any module when $v^{*}(a,b)=\bot$ also counts as output $1$. EvoCrypt is \emph{upgrade sound} if $\mathsf{Adv}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)=\Pr[\mathsf{Exp}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)=1]$ is negligible for every PPT $\mathcal{A}$.
\end{definition}

Definition~\ref{def:sound} is the target property: whatever $\mathcal{A}$ does to scheduling and node-local storage, every honest node that answers an invocation runs exactly the artifact the canonical chain designates for that height. Definitions~\ref{def:div} and~\ref{def:sub} isolate the two ways this can fail.

\subsection{Upgrade Security}\label{sec4.2}

\begin{lemma}[Activation timeliness]
\label{lem:timeliness}
Under Assumption~\ref{asm:committee}, for every honest node $n$ and every $\mu_{a,v}\in\mathsf{Reg}(\mathcal{L}_n)$: (i) $v^{*}_{n}(a,b)\neq v$ for every $b<H_{a,v}$, and (ii) $v$ lies in the feasible set of~\eqref{eq:version-select} at every $b$ with $H_{a,v}\le b\le|\mathcal{L}_n|$.
\end{lemma}

\begin{proof}
(i) The feasible set contains only versions with $H_{a,v}\le b$. (ii) By Assumption~\ref{asm:committee}(ii), $u_{a,v}<H_{a,v}\le b$, so the admitting transaction lies in $\mathcal{L}_n[1..b]$, and by (iii) the record is never removed; hence $\mu_{a,v}\in\mathsf{Reg}(\mathcal{L}_n[1..b])$ and $H_{a,v}\le b$ places $v$ in the feasible set.\qed
\end{proof}

The lemma confines the preparation window of $(a,v)$ to heights $u_{a,v}<b<H_{a,v}$ and excludes retroactive activation: appending a block never changes the version designated for an already-executed height, which is why a node replaying history, such as the late-joining node in Section~\ref{sec5.3}, agrees with nodes that executed it live.

\begin{theorem}[Activation consistency]
\label{thm:activation}
Under Assumptions~\ref{asm:ledger} and~\ref{asm:committee}, every adversary $\mathcal{A}$, including a computationally unbounded one, has $\mathsf{Adv}^{\mathrm{div}}_{\mathcal{A}}(\kappa)=0$.
\end{theorem}

\begin{proof}
Fix any output $(a,b,n,n')$ of $\mathcal{A}$. By Assumption~\ref{asm:ledger}, $P=\mathcal{L}_n[1..b]=\mathcal{L}_{n'}[1..b]$, and by Definition~\ref{def:registry} $\mathsf{Reg}(P)$ is a function of $P$, so both nodes hold the same records and the same feasible set $\{(H_{a,v},v): H_{a,v}\le b\}$. By Assumption~\ref{asm:committee}(iii) its elements are pairwise distinct, so the lexicographic maximum in~\eqref{eq:version-select} is unique when the set is non-empty, and both nodes return $\bot$ when it is empty; hence $v^{*}_{n}(a,b)=v^{*}_{n'}(a,b)$. No adversarial capability enters this computation: scheduling, preparation timing, crashes and artifact tampering act on node-local state, whereas line~\ref{line:resolve} of Algorithm~\ref{alg:invocation-protocol} evaluates~\eqref{eq:version-select} on the registry before any node-local state is consulted. The experiment therefore never outputs $1$, whatever the running time of $\mathcal{A}$.\qed
\end{proof}

Theorem~\ref{thm:activation} is information-theoretic. The next theorem shows that binding the executed bytecode to the registry costs exactly one collision-resistance assumption.

\begin{theorem}[Module binding]
\label{thm:binding}
Under Assumption~\ref{asm:committee}, for every PPT adversary $\mathcal{A}$ there exists a PPT algorithm $\mathcal{B}$, running in the time of $\mathcal{A}$ plus the cost of simulating the honest nodes, such that
\begin{equation}
\mathsf{Adv}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B}).
\label{eq:binding-bound}
\end{equation}
In particular, $\mathsf{Adv}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)$ is negligible under Assumption~\ref{asm:cr}.
\end{theorem}

\begin{proof}
On input $1^{\kappa}$, $\mathcal{B}$ runs $\mathsf{Exp}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)$ internally: it simulates the ledger and every honest node, executing Algorithms~\ref{alg:upgrade-protocol} and~\ref{alg:invocation-protocol} on their behalf, and answers the scheduling and artifact-tampering requests of $\mathcal{A}$ exactly as the real experiment would. The simulation is perfect because the model contains no secret state. Whenever a simulated honest node is about to mark $(a,v)$ prepared with $\widehat{C}$ (Algorithm~\ref{alg:upgrade-protocol}, line~\ref{line:mark-prepared}) or to execute $\widehat{C}$ for $(a,v)$ (Algorithm~\ref{alg:invocation-protocol}, line~\ref{line:execute}), $\mathcal{B}$ reads $C_{a,v}$ from the simulated registry; if $\widehat{C}\neq C_{a,v}$ it outputs $(\widehat{C},C_{a,v})$ and halts, and otherwise it eventually outputs $\bot$.

Let $E$ be the event that $\mathsf{Exp}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)$ outputs $1$; by perfect simulation, $\Pr[E]=\mathsf{Adv}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)$ in the run of $\mathcal{B}$. On $E$, an honest node accepted $\widehat{C}$ for $(a,v)$, which happens only after verifying $\mathrm{Keccak256}(\widehat{C})=h_{a,v}$ against the canonical record (Algorithm~\ref{alg:upgrade-protocol}, line~\ref{line:hash-check}; the prepared set is keyed by $h_{a,v}$, so execution reloads the artifact under the same check). By Assumption~\ref{asm:committee}(i), $h_{a,v}=\mathrm{Keccak256}(C_{a,v})$, so $(\widehat{C},C_{a,v})$ is a collision and $\Pr[E]\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B})$, which is~\eqref{eq:binding-bound}. The reduction is tight: it loses no advantage and does not guess the target record.\qed
\end{proof}

The hash binds only the bytecode; ABI descriptors, gas parameters and Activation Block are read directly from the canonical registry, which Theorem~\ref{thm:activation} already fixes across honest nodes.

\begin{theorem}[Upgrade soundness]
\label{thm:soundness}
Under Assumptions~\ref{asm:ledger}--\ref{asm:cr}, EvoCrypt is upgrade sound: for every PPT adversary $\mathcal{A}$ there exists a PPT $\mathcal{B}$ as in Theorem~\ref{thm:binding} such that
\begin{equation}
\mathsf{Adv}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B}).
\label{eq:soundness-bound}
\end{equation}
\end{theorem}

\begin{proof}
Let $W$ be the event that $\mathsf{Exp}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)$ outputs $1$ at honest node $n$ for an invocation of $a$ at height $b$ executed with $\widehat{C}$; let $v=v^{*}(a,b)$ be the canonical selection, $v_n$ the version resolved by $n$ in line~\ref{line:resolve} of Algorithm~\ref{alg:invocation-protocol}, and $\hat v$ the version under which $\widehat{C}$ was prepared. Then $W\subseteq E_1\cup E_2\cup E_3$ with
\begin{equation*}
E_1 : v_n\neq v,\qquad
E_2 : v_n=v \wedge \hat v\neq v_n,\qquad
E_3 : \hat v=v_n=v \wedge \widehat{C}\neq C_{a,v},
\end{equation*}
since if none occurs then $\widehat{C}=C_{a,v^{*}(a,b)}$.
$\Pr[E_1]=0$: node $n$ evaluates~\eqref{eq:version-select} on $\mathsf{Reg}(\mathcal{L}_n[1..b])$, which by Assumption~\ref{asm:ledger} is the canonical prefix, so the argument of Theorem~\ref{thm:activation} gives $v_n=v$; if $v=\bot$ the node returns a missing-version error (line~\ref{line:missing}) and executes nothing.
$\Pr[E_2]=0$: line~\ref{line:ensure} admits execution only for the resolved pair $(a,v_n)$ and, under the mandatory-preparation policy, continues preparing $(a,v_n)$ rather than falling back to another prepared version, so the only artifact reaching line~\ref{line:execute} was prepared for $(a,v_n)$.
$E_3$ is a module substitution for $(a,v)$ with $\mu_{a,v}\in\mathsf{Reg}(\mathcal{L}_n)$, the latter by Lemma~\ref{lem:timeliness}(ii) since $H_{a,v}\le b$; hence $\Pr[E_3]\le\mathsf{Adv}^{\mathrm{sub}}_{\mathcal{A}}(\kappa)\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B})$ by Theorem~\ref{thm:binding}. A union bound yields~\eqref{eq:soundness-bound}.\qed
\end{proof}

\begin{remark}[Safety versus liveness]
\label{rem:liveness}
Theorems~\ref{thm:activation}--\ref{thm:soundness} are safety statements: an honest node never selects or runs a version other than the canonical one. They do not assert that every node can answer at height $H_{a,v}$; a node still preparing, or in the retry loop of Algorithm~\ref{alg:upgrade-protocol}, defers rather than degrades. Under Assumption~\ref{asm:committee}(iv) and the deterministic validation of Assumption~\ref{asm:runtime}, an admitted artifact validates identically at every honest node, so preparation cannot succeed at one node and fail permanently at another; how quickly it completes is measured in Sections~\ref{sec5.2} and~\ref{sec5.3} rather than proven here.
\end{remark}

\subsection{Invocation Security}\label{sec4.3}

Section~\ref{sec4.2} fixes \emph{which} artifact an honest node executes. This subsection shows that, once Assumption~\ref{asm:runtime} is added, agreement on the artifact lifts to agreement on the invocation outcome and on the resulting EVM state transition. Assumption~\ref{asm:runtime} is the only new ingredient; it is an engineering assumption on the configured WASM Runtime rather than a cryptographic one, and the statements below make its role explicit. An \emph{outcome} of Algorithm~\ref{alg:invocation-protocol} is the pair $(o,\gamma)$, where $o$ is either the ABI-encoded result $y$ or one of the protocol errors returned by the algorithm, and $\gamma$ is the gas charged, with $\gamma=0$ when the algorithm returns before line~\ref{line:execute}.

\begin{definition}[Invocation divergence]
\label{def:inv}
In $\mathsf{Exp}^{\mathrm{inv}}_{\mathcal{A}}(\kappa)$, the adversary finally outputs $(d,g,b,n,n')$ with $n,n'\in\mathcal{N}$ and $b\le\min(|\mathcal{L}_n|,|\mathcal{L}_{n'}|)$, and both nodes run Algorithm~\ref{alg:invocation-protocol} on request $d$ with gas budget $g$ at height $b$. If either node has not produced an outcome, the experiment outputs $0$; otherwise it outputs $1$ iff $(o_n,\gamma_n)\neq(o_{n'},\gamma_{n'})$. $\mathsf{Adv}^{\mathrm{inv}}_{\mathcal{A}}(\kappa)=\Pr[\mathsf{Exp}^{\mathrm{inv}}_{\mathcal{A}}(\kappa)=1]$.
\end{definition}

Returning $0$ when a node has not answered keeps the definition a safety property, in line with Remark~\ref{rem:liveness}: a node still preparing at line~\ref{line:ensure} defers and is not counted as disagreeing.

\begin{lemma}[Pre-execution agreement]
\label{lem:preexec}
Under Assumptions~\ref{asm:ledger} and~\ref{asm:committee}, two honest nodes running Algorithm~\ref{alg:invocation-protocol} on the same $(d,g,b)$ take the same branch at every line before line~\ref{line:execute}, resolve the same version $v=v^{*}(a,b)$, and compute the same $G_{\mathrm{req}}=G(a,v,x)$. In particular, if either node returns an ABI, missing-version or out-of-gas error, both return the same error with $\gamma=0$.
\end{lemma}

\begin{proof}
$\mathrm{Parse}$ is a fixed function of $d$, so both nodes obtain the same $(a,x)$ or the same ABI error. Theorem~\ref{thm:activation} gives $v^{*}_{n}(a,b)=v^{*}_{n'}(a,b)$, so the missing-version test agrees. If a version is resolved, both nodes read $\mu_{a,v}$ from $\mathsf{Reg}(\mathcal{L}_n[1..b])=\mathsf{Reg}(\mathcal{L}_{n'}[1..b])$ (Assumption~\ref{asm:ledger} with Definition~\ref{def:registry}), hence the same $g^{(0)}_{a,v}$, $\lambda_{a,v}$, $\tau^{\mathrm{in}}_{a,v}$ and $\tau^{\mathrm{out}}_{a,v}$. Since $|x|$ is determined by $d$, \eqref{eq:gas-price} yields the same $G_{\mathrm{req}}$, and comparison with the common budget $g$ yields the same out-of-gas decision. None of these steps reads node-local state other than the prepared set, which only decides whether line~\ref{line:ensure} must prepare first, not which branch is taken.\qed
\end{proof}

\begin{theorem}[Invocation consistency]
\label{thm:invocation}
Under Assumptions~\ref{asm:ledger}--\ref{asm:runtime}, for every PPT adversary $\mathcal{A}$ there exists a PPT $\mathcal{B}$ as in Theorem~\ref{thm:binding} such that
\begin{equation}
\mathsf{Adv}^{\mathrm{inv}}_{\mathcal{A}}(\kappa)\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B}).
\label{eq:inv-bound}
\end{equation}
Moreover, whenever both nodes answer, they charge the same gas unconditionally: $\gamma_n=\gamma_{n'}=G(a,v^{*}(a,b),x)$ if line~\ref{line:execute} is reached and $\gamma_n=\gamma_{n'}=0$ otherwise.
\end{theorem}

\begin{proof}
Let $W$ be the event that $\mathsf{Exp}^{\mathrm{inv}}_{\mathcal{A}}(\kappa)$ outputs $1$, so both nodes answered and $(o_n,\gamma_n)\neq(o_{n'},\gamma_{n'})$. Let $v=v^{*}(a,b)$, and let $\widehat{C}_n,\widehat{C}_{n'}$ be the byte sequences the nodes execute at line~\ref{line:execute} when they reach it. Then $W\subseteq F_1\cup F_2\cup F_3$ with
\begin{align*}
F_1 &: \text{the nodes take different branches before line~\ref{line:execute}},\\
F_2 &: \text{both reach line~\ref{line:execute} and } \widehat{C}_n\neq C_{a,v}\ \vee\ \widehat{C}_{n'}\neq C_{a,v},\\
F_3 &: \widehat{C}_n=\widehat{C}_{n'}=C_{a,v}\ \wedge\ o_n\neq o_{n'},
\end{align*}
since if none occurs, both nodes either return the same pre-execution error with $\gamma=0$, or reach line~\ref{line:execute} with the same $G_{\mathrm{req}}$, execute the same bytecode and return the same $o$.
$\Pr[F_1]=0$ by Lemma~\ref{lem:preexec}.
$F_2$ states that some honest node executes an invocation of $a$ at height $b$ with bytecode other than $C_{a,v^{*}(a,b)}$, which is exactly the winning event of $\mathsf{Exp}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)$; hence $\Pr[F_2]\le\mathsf{Adv}^{\mathrm{bind}}_{\mathcal{A}}(\kappa)\le\mathsf{Adv}^{\mathrm{cr}}_{\mathrm{Keccak256}}(\mathcal{B})$ by Theorem~\ref{thm:soundness}. The bound covers both nodes at once because $\mathsf{Exp}^{\mathrm{bind}}$ already quantifies over all honest nodes.
$\Pr[F_3]=0$: on $F_3$ both nodes evaluate $\mathsf{Exec}(C_{a,v},x)$ on the same arguments, and by Assumption~\ref{asm:runtime} its output, including any runtime error, is a function of $(C_{a,v},x)$ and the fixed host interface; ABI encoding of that output under the common $\tau^{\mathrm{out}}_{a,v}$ is deterministic, so $o_n=o_{n'}$.
A union bound gives~\eqref{eq:inv-bound}. The gas statement is Lemma~\ref{lem:preexec}: $\gamma$ equals $G_{\mathrm{req}}$ when line~\ref{line:execute} is reached and $0$ otherwise, and both quantities agree without any computational assumption.\qed
\end{proof}

The bound in~\eqref{eq:inv-bound} coincides with that of Theorem~\ref{thm:soundness}: adding Assumption~\ref{asm:runtime} introduces no further probabilistic loss, and the charged gas is agreed unconditionally. The latter is the formal counterpart of Definition~\ref{def:gas-schedule}: because $G$ depends only on registry fields and $|x|$, no node-local measurement enters the fee, and differences in CPU time or in the number of WASM instructions executed cannot make honest nodes charge differently.

\subsection{Residual Risks and Governed Recovery}\label{sec4.4}

Two risks remain inside the model of Section~\ref{sec4.1} after Theorems~\ref{thm:activation}--\ref{thm:invocation}: an admitted implementation may later prove unsuitable or vulnerable, and an admitted gas schedule may underprice or overprice the resources a call consumes. Neither is excluded by the committee review of Assumption~\ref{asm:committee}, which is trusted but not infallible. EvoCrypt does not prevent such admissions; it guarantees that a governed correction, once admitted, takes effect at every honest node and renders the faulty version unreachable.

\begin{corollary}[Governed supersession]
\label{cor:supersession}
Under Assumptions~\ref{asm:ledger} and~\ref{asm:committee}, let $\mu_{a,v}$ and $\mu_{a,v'}$ be admitted with $H_{a,v'}>H_{a,v}$. Then for every honest node $n$ and every height $H_{a,v'}\le b\le|\mathcal{L}_n|$, $v^{*}_{n}(a,b)\neq v$. If, moreover, no admitted version of $a$ other than $v'$ has an activation height in $[H_{a,v'},b]$, then $v^{*}_{n}(a,b)=v'$.
\end{corollary}

Corollary~\ref{cor:supersession} covers the three corrective actions. \emph{Replacement} admits $\mu_{a,v'}$ with new bytecode; from $H_{a,v'}$ on, Theorem~\ref{thm:soundness} guarantees that every honest node runs $C_{a,v'}$ and never $C_{a,v}$. \emph{Repricing} admits $\mu_{a,v'}$ with revised $g^{(0)}_{a,v'},\lambda_{a,v'}$ and possibly unchanged bytecode, which Assumption~\ref{asm:committee}(iii) permits because uniqueness is over $(a,v)$ rather than over $h_{a,v}$; Lemma~\ref{lem:preexec} then charges the new fee unconditionally. \emph{Deprecation} admits a version whose module returns a protocol error on every input, so that by Theorem~\ref{thm:invocation} all invocations of $a$ fail deterministically after $H_{a,v'}$ without any contract redeployment. In each case, the correction becomes effective exactly $H_{a,v'}-u_{a,v'}$ blocks after admission, and a node is ready at that height whenever its preparation completes within this window (Remark~\ref{rem:liveness}); Section~\ref{sec5.2} measures the preparation time that this window must cover.

\subsection{Upgrade Consistency}\label{sec5.3}

The consistency experiment showed that the evaluated nodes followed the same activation decision after an upgrade was registered, even though event handling and WASM preparation remained node-local. As illustrated in Figure~\ref{fig:consistency-scene}, the upgrade transaction records version metadata on chain, nodes prepare the corresponding WASM module, and invocations at or after the Activation Block resolve to the same active version through the canonical version-selection rule. In the evaluated 20-node private Clique network, complete Geth-side upgrade handling finished within 0.54--2.34~ms across the eight algorithms, and the observed activation path produced a common callable version after preparation completed on all evaluated nodes. This supports the intended consistency property of EvoCrypt: local readiness affects preparation timing, whereas version selection is fixed by shared on-chain metadata and block height rather than local event timing. The experiment is nevertheless a controlled private-network validation; it does not measure wide-area propagation, adversarial scheduling, consensus delay under nonzero block periods, or governance failures.

\section{Conclusion}\label{sec6}

EvoCrypt addresses the problem of evolving contract-facing cryptographic capabilities without embedding complex algorithms in EVM bytecode or modifying the client for every update. Its design separates the stable contract-facing interface from replaceable client-side WASM implementations, while deterministic version selection and algorithm-level accounting preserve consistent invocation rules.

Three bounded conclusions follow from the evaluated prototype. EvoCrypt lowers the implementation burden by moving complex cryptographic logic out of Solidity and into replaceable WASM modules, reduces the evaluated calling cost under the experimental gas schedule, and provides a dynamic upgrade mechanism that lets smart contracts evolve their cryptographic capabilities without changing their contract-facing interface. Algorithm execution remains slower than suitable Precompiled Contracts, and the current gas parameters are not economically calibrated. Future work will refine resource pricing and evaluate broader deployment and security conditions.
