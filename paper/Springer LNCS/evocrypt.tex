\begin{abstract}
Smart contracts frequently rely on cryptographic algorithms, yet implementing complex cryptographic computation in Solidity expands it into large sequences of EVM instructions, resulting in substantial execution overhead and gas consumption. Precompiled Contracts reduce these costs by exposing client-side routines at fixed addresses, but they provide no runtime mechanism for evolving an algorithm independently of client releases and coordinated network upgrades. We present EvoCrypt, an upgradeable cryptographic coprocessor framework  that exposes a stable contract-facing interface while executing replaceable WebAssembly (WASM) modules in a controlled client-side runtime. EvoCrypt distributes version metadata on-chain and deterministically activates an installed module at a designated block height, allowing participating nodes to switch algorithm versions consistently. Each invocation is charged according to a deterministic algorithm-level gas schedule associated with the activated version, thereby avoiding the cost of expanding the algorithm into EVM instructions while retaining explicit resource accounting. We implement EvoCrypt in Geth and evaluate it on a 20-node private network. The experiments show that EvoCrypt improves the efficiency of contract-facing cryptographic upgrades and invocations compared with Solidity-based implementations, while retaining near-Precompiled-Contract execution costs for most benchmark algorithms. EvoCrypt also supports the deployment of complex cryptographic algorithms that are difficult to realize directly in the EVM ecosystem.

\keywords{blockchain \and smart contracts \and upgrade \and WebAssembly}
\end{abstract}

\section{Introduction}\label{sec1}

As blockchain systems become programmable platforms, smart contracts increasingly depend on cryptographic algorithms for authentication, integrity, signatures, and privacy \cite{nakamoto2008bitcoin,zou2021smartContracts,woodEthereumYellowPaper,ethereumEVM}. The long-term security of these applications also requires the ability to adopt new algorithms, including post-quantum alternatives, without disrupting contract-facing functionality \cite{shor1999,grover1996,nistPqcProject}. Blockchain clients therefore need an extensible way to provide evolving cryptographic capabilities to smart contracts.

Ethereum provides two main mechanisms for executing cryptographic operations: Solidity contract implementations and Precompiled Contracts. Solidity implementations are flexible and deployable at the contract layer, but complex cryptographic computation expands into costly EVM execution; Precompiled Contracts execute selected routines efficiently in client-side code, but their supported algorithms are fixed to the client and normally require coordinated client updates to change \cite{woodEthereumYellowPaper,ethereumEVM,evmCodesPrecompiled}.

Together, these mechanisms expose a fundamental trade-off between execution efficiency and algorithm upgradability. Solidity keeps algorithms deployable without client changes but can impose substantial execution and gas overhead, whereas Precompiled Contracts provide efficient execution only for routines embedded in the client and are therefore difficult to evolve independently. The central challenge is to replace contract-facing cryptographic implementations without sacrificing efficient execution, deterministic behavior across nodes, or compatibility with the existing EVM interface.

EvoCrypt addresses this trade-off by separating the stable contract-facing interface from replaceable WASM implementations and by separating module preparation from module activation. The interface preserves how smart contracts invoke cryptographic operations, while portable WASM modules allow implementations to be replaced without embedding each algorithm in contract bytecode or rebuilding the client for every change. Asynchronous preparation moves verification, compilation, and instantiation away from the transaction execution path. Activation-Block-based selection then ensures that nodes switch versions according to a common chain-derived rule rather than local readiness time. The design combines algorithm-level accounting with deterministic, incrementally deployable upgrades.

The main contributions of this article are summarized as follows.
\begin{itemize}
    \item First, we design an upgradeable cryptographic coprocessor that separates the stable contract-facing interface from replaceable WASM-based algorithm implementations, allowing complex cryptographic operations to execute outside the EVM while preserving contract compatibility.
    \item Second, we design an activation-block-based upgrade protocol in which upgrade proposals are published on-chain, ensuring that clients derive the same proposal from a common authoritative record. By distributing and verifying a uniform WASM bytecode artifact, the protocol further ensures consistent module execution across clients when the upgrade becomes active.
    \item Finally, we implement EvoCrypt in Geth and evaluate it on a 20-node private blockchain network. The results show that EvoCrypt reduces the implementation burden and calling cost of the evaluated cryptographic operations while supporting dynamic evolution of contract-facing algorithms.
\end{itemize}

\section{Related Work}\label{sec2}

Research on cryptographic algorithm upgrades in blockchain systems has not yet resolved the combined problem of efficient invocation and practical implementation. Related approaches can be organized by the layer at which they support upgrades: protocol and client, contract, or dynamic runtime.

Existing blockchain upgrade schemes primarily replace code at the protocol or client level, where a coordinated version transition preserves a common execution rule across nodes. Cardano's hard-fork combinator moves the chain between protocol eras at designated upgrade points, while work on updatable blockchains studies synchronization between old and new chains \cite{cardanoHardForkCombinator,cardanoEvolution,ciampi2020updatable}. Soft-fork approaches instead place selected policy changes within rules that can be adopted without replacing the entire protocol \cite{zindros2021softPower}. Phoenix and Polkadot are closest to EvoCrypt in that both support live replacement. Phoenix carries upgrade code in blockchain transactions and compiles it at runtime, whereas Polkadot stores governance-approved WASM runtime logic on chain and replaces the state-transition logic during block synchronization \cite{wang2023phoenix,polkadotRuntimeUpgrades}. Their replacement targets are nevertheless different from contract-facing cryptographic algorithms. These systems mainly upgrade blockchain-client or chain-runtime components; they do not define how a smart contract names an algorithm, binds to a compatible input-output interface, pays invocation cost, and selects a new algorithm version at a block height without redeploying the calling contract. EvoCrypt narrows the replacement boundary to individual cryptographic modules behind a stable Solidity-facing interface. In this design, WASM is an algorithm artifact rather than a whole-chain runtime, and consistency is derived from hash-identified module metadata, activation height, and per-algorithm resource parameters.

Contract-level schemes update application logic without replacing the entire blockchain client, using deployable contracts, proxy indirection, or bytecode rewriting. EVMPatch patches deployed Ethereum smart contracts through bytecode rewriting and proxy-based deployment, while Solidity implementations offer application-level flexibility within the EVM \cite{rodler2021evmpatch,ethereumEVM}. LEAGAN extends contract-level upgradeability through data separation, incremental hashing, revision control, and status-contract-based version management \cite{kumar2025leagan}. Precompiled Contracts provide a complementary client-side path for selected cryptographic routines through reserved EVM-facing addresses \cite{evmCodesPrecompiled,eip196,eip197}. Contract-level implementations remain constrained by EVM execution cost and state or interface compatibility, whereas adding or replacing a Precompiled Contract normally requires changes to client and protocol rules.

Dynamic software-update schemes move replacement below the application layer by loading new components into a running host, with emphasis on availability, version compatibility, or isolation. KylinX supports runtime library replacement through dynamic mapping, Mvedsua combines dynamic updates with multi-version execution, PYLIVE changes Python code online, and distributed-system research addresses modular updates and version consistency \cite{zhang2018kylinx,pina2019mvedsua,huang2021pylive,ajmani2006modular,baresi2017versionConsistency}. WASM provides a portable artifact format and explicit host boundary for this style of replacement. In blockchain systems, existing WASM-based upgrades generally target broad runtime logic rather than a narrow EVM-facing cryptographic interface \cite{webassemblyCoreSpec,polkadotRuntimeUpgrades}.


\section{EvoCrypt Design}\label{sec3}

EvoCrypt is a cryptographic coprocessor framework for dynamically upgrading contract-facing cryptographic algorithms. This section presents the system model, the upgrade protocol, and the invocation protocol that together define the design. We focus on the coordination, version-selection, and contract-facing execution rules of EvoCrypt, while the prototype implementation and experimental configuration are described in Section~\ref{sec5}.

\subsection{System Model}\label{sec3.1}
EvoCrypt separates governance, chain state, contract execution, and module execution into four cooperating components: the Community, the Blockchain, the EVM, and the Cryptographic Coprocessor. The Community includes developers and an authorizing committee that proposes and approves algorithm upgrades. The Blockchain maintains the canonical chain and shared world state, including smart contracts and the Management Contract. The EVM processes smart-contract transactions, while the node-local Cryptographic Coprocessor prepares, activates, and executes replaceable cryptographic modules.

Two chain-derived paths connect these components. An approved proposer records an upgrade through the Management Contract, whereas a contract initiates an invocation through the EVM of a Blockchain node. The Management Contract stores algorithm metadata and exposes the contract-facing upgrade and invocation interfaces. The coprocessor uses the resulting chain state to prepare and execute the corresponding module. Figure~\ref{fig:overview} summarizes these objects and their relationships.

\subsection{Upgrade Protocol}\label{sec3.2}
\noindent\textbf{On-chain publication.} On-chain publication provides the authoritative record that coordinates node-local preparation and height-based activation. After the committee approves a proposal, a committee-authorized proposer submits it through the designated upgrade interface. The Management Contract admits the proposal only after the committee has reached consensus on its contents, stores the version metadata, and emits an upgrade event.

The EVM records metadata but does not compile or instantiate the WASM module. Node-dependent preparation therefore remains outside the transaction that changes the chain state. Every node reconstructs the same version from the admitted record, which identifies the algorithm, version, WASM artifact, module hash, interface descriptors, resource parameters, and Activation Block. Only $\langle a,v,H_{a,v}\rangle$ is emitted as a notification index. Let $\mathcal{V}_{a}$ denote the versions already registered for algorithm $a$; the authoritative record prevents nodes from preparing different artifacts or execution rules for the same upgrade.

\begin{definition}[Version metadata]
\label{def:version-metadata}
Let $a$ be an algorithm name and $v$ a version number. An admitted upgrade is the metadata record
\begin{equation}
\mu_{a,v}=\bigl(a,\,v,\,C_{a,v},\,h_{a,v},\,g^{(0)}_{a,v},\,\lambda_{a,v},\,\tau^{\mathrm{in}}_{a,v},\,\tau^{\mathrm{out}}_{a,v},\,H_{a,v}\bigr),
\label{eq:version-metadata}
\end{equation}
where $C_{a,v}$ is the compiled WASM bytecode, $h_{a,v}=\mathrm{Keccak256}(C_{a,v})$ is the module hash, $g^{(0)}_{a,v}$ is the initial gas fee, $\lambda_{a,v}$ is the gas slope parameter, $\tau^{\mathrm{in}}_{a,v}$ and $\tau^{\mathrm{out}}_{a,v}$ are the ABI input and output type descriptors, and $H_{a,v}$ is the Activation Block height. The Management Contract stores an encoding of these fields. Each node recomputes $h_{a,v}$ from the recovered bytecode during preparation and binds that hash to the prepared version.
\end{definition}

\noindent\textbf{Node-local preparation.} Node-local preparation converts the admitted metadata record into executable state without changing the active version. After observing the upgrade event, each client recovers $\mu_{a,v}$, checks that the event index agrees with the stored record, decodes the artifact, and recomputes its hash. The Upgrade Handler then compiles and instantiates the module and validates its required entry point. Once these checks succeed, the node records $(a,v)$ as prepared. Algorithm~\ref{alg:upgrade-protocol} gives the complete publication and preparation procedure.

Preparation is deliberately separated from the chain-level upgrade record. Node-local work can proceed asynchronously, failed attempts can retry from the authoritative chain record, and an executed upgrade transaction is not rolled back. The separation allows preparation to complete without changing the version selected by the chain.

\begin{algorithm}[!htb]
\caption{\textbf{Activation-Block-based WASM upgrade protocol.}}
\label{alg:upgrade-protocol}
\begin{algorithmic}[1]
\Require Metadata $\mu_{a,v}$ as in~\eqref{eq:version-metadata}; node set $\mathcal{N}$
\Ensure Prepared set updated on every $n_i\in\mathcal{N}$
\State committee-authorized proposer submits $\mu_{a,v}$ through the designated upgrade interface
\State Management Contract stores $\mu_{a,v}$; emits event $\langle a,v,H_{a,v}\rangle$
\ForAll{$n_i\in\mathcal{N}$}
    \State observe $\langle a,v,H_{a,v}\rangle$; fetch $\mu'_{a,v}$ from Management Contract
    \If{event fields disagree with $\mu'_{a,v}$}
        \State reject $(a,v)$
    \Else
        \State decode $C_{a,v}$; set $h_{a,v}\gets\mathrm{Keccak256}(C_{a,v})$
        \Repeat
        \State compile and instantiate; validate the required module entry point
        \Until{preparation succeeds}
        \State persist $h_{a,v}$ and $\mu_{a,v}$; mark $(a,v)$ prepared
    \EndIf
\EndFor
\end{algorithmic}
\end{algorithm}

\noindent\textbf{Height-based activation.} Height-based activation makes the selected version a function of shared chain height rather than node-local preparation time. The Upgrade Block includes the admitted upgrade transaction and emits $\langle a,v,H_{a,v}\rangle$. After that block, each node independently completes the off-chain Load--Verify--Ready sequence, while invocations before $H_{a,v}$ continue to use the previously selected version. At the Activation Block, nodes with the same chain view select version $v$ according to the rule below. Compilation-time differences therefore cannot change the version selected at a given execution height.

When a selected version is not yet prepared, the node reloads its authoritative metadata and continues preparation rather than selecting an obsolete version. The policy preserves height-based selection while allowing node-local readiness to complete asynchronously. Figure~\ref{fig:upgrade-protocol} shows the separation between publication, preparation, and activation.

\begin{definition}[Active version]
\label{def:active-version}
Let $\mathcal{V}_{a}$ be the registered version set of algorithm $a$, and let $b$ be the execution block height. The version used at height $b$ is
\begin{equation}
v^{*}(a,b)=
\underset{v \in \mathcal{V}_{a}}{\arg\max}
\left\{
\left(H_{a,v},\,v\right)
\;\middle|\;
H_{a,v} \leq b
\right\}.
\label{eq:version-select}
\end{equation}
The $\arg\max$ is lexicographic on the pair $(H_{a,v},v)$: among versions whose activation height does not exceed $b$, the rule prefers the latest activation height and, for a tied height, the larger version number. If the feasible set is empty, no version is active and the invocation fails with a missing-version error.
\end{definition}

\subsection{Invocation Protocol}\label{sec3.3}
A unified Management Contract entry point preserves a stable contract-facing invocation boundary. A caller serializes the algorithm name $a$ and its parameters into an encoded request $x$ and submits the request through the designated interface. Different algorithms can therefore be invoked without changing the destination address, while upgrade and invocation events remain associated with one on-chain management endpoint. The contract depends on the ABI descriptors of the selected version rather than on the module location, implementation language, or node-local loading state.

Version resolution precedes execution. If the selected version is not yet prepared, the coprocessor prepares it rather than redirecting the request to an obsolete implementation.

EVM-side Hooks determine whether a request enters the Cryptographic Coprocessor. Requests that do not target the designated invocation interface remain on the ordinary EVM execution path. For a routed request, the coprocessor parses $(a,x)$, resolves $v^{*}(a,b)$ by~\eqref{eq:version-select}, and prepares the selected version if necessary. The selected module receives the encoded parameters and returns an encoded result; the contract-facing call shape remains compatible when $\tau^{\mathrm{in}}_{a,v}$ and $\tau^{\mathrm{out}}_{a,v}$ are compatible.

Routing is followed by version resolution, optional preparation, deterministic charging, and module execution. Algorithm~\ref{alg:invocation-protocol} specifies this post-routing procedure and its protocol-error conditions.

\begin{definition}[Algorithm-level gas schedule]
\label{def:gas-schedule}
Each algorithm version uses an independent deterministic pricing rule so that its fee can reflect the resource class of the algorithm while remaining identical across clients. A call with inner input $x$ against version $v$ of algorithm $a$ is charged
\begin{equation}
G(a,v,x)=g^{(0)}_{a,v}+\lambda_{a,v}\cdot |x|,
\label{eq:gas-price}
\end{equation}
where $|x|$ is the byte length of the call-stage inner input, $g^{(0)}_{a,v}$ is the initial gas fee, and $\lambda_{a,v}$ is the gas slope parameter registered in $\mu_{a,v}$. The charged amount does not depend on node-local CPU time or on the number of WASM instructions executed inside the module.
\end{definition}

\begin{algorithm}[!htb]
\caption{\textbf{Contract-to-coprocessor invocation protocol.}}
\label{alg:invocation-protocol}
\begin{algorithmic}[1]
\Require Recognized invocation request $d$, block height $b$, gas budget $g$
\Ensure ABI-encoded result $y$ or explicit error
\State $(a,x)\gets\mathrm{Parse}(d)$
\If{the request is invalid}
    \State \textbf{return} ABI error
\EndIf
\State $v\gets v^{*}(a,b)$ by~\eqref{eq:version-select}
\If{no applicable version exists}
    \State \textbf{return} missing-version error
\EndIf
\State ensure $(a,v)$ is prepared under the mandatory-preparation policy
\State $G_{\mathrm{req}}\gets G(a,v,x)$ by~\eqref{eq:gas-price}
\If{$g<G_{\mathrm{req}}$}
    \State \textbf{return} out-of-gas error
\EndIf
\State charge $G_{\mathrm{req}}$; $y\gets\mathrm{Execute}(a,v,x)$
\State \textbf{return} $y$, or runtime error on failure
\end{algorithmic}
\end{algorithm}

For each algorithm version, the algorithm-level schedule accounts for input-sensitive resource demand without relying on node-local measurements. Its coefficients assign a fixed cost, a length-dependent cost, or both to each algorithm version. Consequently, the schedule remains independent of local CPU time, runtime fluctuations, and the number of WASM instructions observed by an individual client.

With this fixed-plus-length form, every node that resolves the same $v^{*}(a,b)$ and receives the same input charges an identical fee. The schedule follows the deterministic pricing intuition of Precompiled Contracts while retaining an input-sensitive component. Coefficients used in Section~\ref{sec5} demonstrate the pricing mechanism rather than a calibrated economic optimum.

\section{Security Analysis}\label{sec4}

This chapter establishes the security boundaries of EvoCrypt under explicit trust assumptions. It explains how canonical metadata and deterministic version selection support upgrade and invocation consistency, and how the WASM runtime limits host-resource exposure while preserving online governance.

\subsection{Security Model}\label{sec4.1}
The security model considers a private blockchain maintained by multiple nodes that implement the EvoCrypt framework, including the Management Contract state and each node-local coprocessor. For an algorithm $a$ and version $v$, let $\mu_{a,v}$ denote the authoritative metadata record, let $C_{a,v}$ denote its encoded WASM bytecode, let $h_{a,v}$ denote the recorded module hash, let $H_{a,v}$ denote the Activation Block, and let $v^{*}(a,b)$ be the version selected at execution height $b$ according to~\eqref{eq:version-select}. Security claims concern honest nodes that execute the same canonical chain and therefore observe the same committed Management Contract state.

Each admitted proposal is assumed to be registered in the canonical Management Contract state before its Activation Block. The record includes the algorithm metadata, bytecode reference, gas parameters, ABI descriptors, and Activation Block. Activation therefore selects a proposal already present in the committed history rather than registering or modifying one at the height at which it becomes active.

Four conditions define the trusted base. The underlying consensus protocol provides a common canonical chain to honest nodes. The committee correctly authorizes upgrades and reviews both the algorithm implementation and its gas schedule before admitting metadata. $\mathrm{Keccak256}$ is collision resistant. Finally, the configured WASM Runtime and controlled host interface implement deterministic ABI handling, WASM execution, host-interface responses, and initial instance state while enforcing resource limits, import validation, and error semantics. The runtime does not expose uncontrolled external state or host capabilities that can affect execution.

The adversary may choose arbitrary contract inputs, observe upgrade events, exploit asynchronous node-local preparation, and submit malformed or resource-intensive upgrade candidates, but admission remains subject to committee review and node-side validation. The model excludes a compromised Geth binary, a broken consensus protocol, a captured committee, failure of the designated implementation review, and a cryptographic primitive whose mathematical assumption is false.

\subsection{Upgrade Security}\label{sec4.2}

\begin{lemma}[Module binding]
Suppose an honest node prepares bytecode $\widehat{C}$ for version $(a,v)$ and accepts it only after checking $\mathrm{Keccak256}(\widehat{C})=h_{a,v}$. Under collision resistance, $\widehat{C}$ is computationally bound to the bytecode identified by the authoritative hash record. The hash check does not bind the ABI descriptors, gas parameters, or Activation Block: these fields are obtained from the authoritative Management Contract state and are interpreted by the version-selection rule.
\end{lemma}

\begin{proof}
Hash recomputation over the recovered byte sequence is compared with $h_{a,v}$. If an adversary could cause two distinct byte sequences to pass this check for the same record, it would produce a collision in $\mathrm{Keccak256}$. Therefore, except with negligible probability under the collision-resistance assumption, the prepared bytecode is the bytecode named by the recorded hash. The remaining metadata fields are not inputs to this comparison; the canonical Management Contract state fixes them.\hfill$\square$
\end{proof}

\begin{theorem}[Activation consistency]
For any two honest nodes with the same canonical chain and execution height $b$, the nodes select the same active version $v^{*}(a,b)$. For a revision registered before its Activation Block, a node that has completed preparation switches to the selected revision at and after that height, whereas a node whose preparation is incomplete continues attempting the update and does not select an obsolete version. Hence, node-local preparation time affects readiness but cannot change the canonical version selected for the same block.
\end{theorem}

\begin{proof}
The canonical chain determines the same Management Contract state, and therefore the same feasible set of records satisfying $H_{a,v}\leq b$. The lexicographic $\arg\max$ in~\eqref{eq:version-select} is deterministic, so both nodes select the same pair $(H_{a,v},v)$ and the same $v^{*}(a,b)$. The pre-activation registration assumption ensures that this record is already available in the committed history when the height-based rule selects it. Preparation affects whether a node is ready to execute the selected version, but it does not affect version selection. A node that is not ready continues its preparation procedure rather than using an obsolete implementation. Thus local preparation differences change readiness timing, not the version selected by the canonical rule.\hfill$\square$
\end{proof}

\subsection{Invocation Security}\label{sec4.3}

\begin{theorem}[Invocation consistency]
Consider two honest nodes processing the same invocation at block height $b$. If they have the same pre-state, request $(a,x)$, gas budget, canonical Management Contract state, prepared bytecode, ABI descriptors, host-interface responses, and initial module state, then they produce the same ABI result or protocol error and charge the same gas $G(a,v^{*}(a,b),x)$.
\end{theorem}

\begin{proof}
Activation consistency gives both nodes the same $v^{*}(a,b)$. Equal authoritative metadata then gives them the same ABI descriptors, gas parameters, and value of~\eqref{eq:gas-price}. Common ABI rules yield the same decoded input and encoded output shape.

Given the same bytecode, deterministic WASM execution, deterministic host-interface responses, and identical initial instance state, the module execution is the same transition from the same module state and input. If execution succeeds, both nodes return the same result; if it violates the specified runtime or protocol conditions, both nodes return the same protocol error.\hfill$\square$
\end{proof}

\begin{corollary}[State-transition consistency]
Under the hypotheses of the invocation-consistency theorem, the two nodes apply the same EVM state transition for the invocation, including the same gas charge and success or failure outcome.
\end{corollary}

\begin{proof}
The invocation protocol resolves the version and gas requirement before executing the module. The theorem establishes equality of the selected version, decoded request, gas charge, module result or protocol error, and encoded return value. The EVM therefore receives the same execution outcome from the coprocessor while starting from the same pre-state. Deterministic EVM execution then yields the same post-state.\hfill$\square$
\end{proof}

\begin{proposition}[Conditional execution isolation]
Let $\mathcal{R}_{\mathrm{prot}}$ be the set of host resources outside the resources explicitly authorized for a call, including Geth process memory other than the designated input and output buffers, local files, network sockets, and mutable host state not exposed by the coprocessor interface. If the WASM Runtime enforces bounded linear memory and validates imports against an allowlist, and if each permitted host function exposes no capability to access $\mathcal{R}_{\mathrm{prot}}$, then an admitted module has no modeled execution path to read or modify $\mathcal{R}_{\mathrm{prot}}$.
\end{proposition}

\begin{proof}
A module can affect its environment only through its own linear memory and the host functions made available to it. The memory boundary prevents direct pointer-based access to the Geth address space, while import validation removes undeclared host capabilities. By assumption, the remaining host functions do not provide indirect access to protected resources. The conclusion is therefore a conditional isolation claim about the runtime boundary. It does not imply that the approved algorithm is free of a cryptographic backdoor, that its mathematical security is established, or that resource exhaustion is impossible within the configured limits.
\hfill$\square$
\end{proof}

\subsection{Governed Security Maintenance}\label{sec4.4}

EvoCrypt treats cryptographic evolution as a governed control action rather than an unconstrained runtime replacement. The upgrade protocol records the admitted algorithm version, WASM hash, ABI descriptors, gas parameters, and Activation Block in the Management Contract state. This on-chain control plane allows honest nodes to check the same governance decision before the corresponding version becomes callable.

This mechanism supports security maintenance in three ways. First, gas parameters can be revised through a new admitted version when an earlier schedule underprices resource consumption or overprices legitimate use. Second, an unsuitable, obsolete, or vulnerable implementation can be superseded by a later version whose bytecode is bound to a new hash and activated at a designated block height. Third, an algorithm can be deprecated by governance policy so that future invocations no longer route to the obsolete version after the replacement becomes active.

These properties do not prove that every admitted algorithm is cryptographically secure or economically well priced. They ensure that, once governance admits a correction, honest nodes have a deterministic and verifiable mechanism for applying it. The security boundary therefore depends on committee authorization, implementation review, and gas-schedule assessment, while EvoCrypt provides the protocol machinery that makes corrective actions consistent across participating nodes.

Collectively, the results give EvoCrypt a bounded security argument. Authoritative on-chain metadata and Activation-Block selection prevent version divergence under a common chain view. Deterministic runtime conditions extend consistency from version selection to invocation outcomes and EVM state transitions. The WASM boundary provides conditional host-resource isolation, while the governed upgrade path supports algorithm replacement, gas-schedule revision, and deprecation of unsuitable algorithms without a client restart.

\section{Evaluation}\label{sec5}

This evaluation asks whether EvoCrypt makes upgradeable cryptographic algorithms practical for contract-facing use. We measure the cost of making an algorithm callable and the steady-state invocation cost, comparing the coprocessor path with Solidity and Precompiled Contract baselines where appropriate.

\subsection{Implementation}\label{sec5.1}

Experiments used a Geth-based private Clique network running modified Geth v1.17.5-unstable on a 16-core, 32~GB Aliyun server with Ubuntu 24.04 LTS, built with Go 1.25.7. Solidity contracts were compiled with solc 0.8.26, and WASM modules were built with TinyGo 0.42.0.

\subsection{Upgrade Consistency}\label{sec5.3}

The consistency experiment showed that the evaluated nodes followed the same activation decision after an upgrade was registered, even though event handling and WASM preparation remained node-local. As illustrated in Figure~\ref{fig:consistency-scene}, the upgrade transaction records version metadata on chain, nodes prepare the corresponding WASM module, and invocations at or after the Activation Block resolve to the same active version through the canonical version-selection rule. In the evaluated 20-node private Clique network, complete Geth-side upgrade handling finished within 0.54--2.34~ms across the eight algorithms, and the observed activation path produced a common callable version after preparation completed on all evaluated nodes. This supports the intended consistency property of EvoCrypt: local readiness affects preparation timing, whereas version selection is fixed by shared on-chain metadata and block height rather than local event timing. The experiment is nevertheless a controlled private-network validation; it does not measure wide-area propagation, adversarial scheduling, consensus delay under nonzero block periods, or governance failures.

The Precompiled Contract path had the shortest algorithm execution time across the evaluated algorithms. \section{Conclusion}\label{sec6}

EvoCrypt addresses the problem of evolving contract-facing cryptographic capabilities without embedding complex algorithms in EVM bytecode or modifying the client for every update. Its design separates the stable contract-facing interface from replaceable client-side WASM implementations, while deterministic version selection and algorithm-level accounting preserve consistent invocation rules.

Three bounded conclusions follow from the evaluated prototype. EvoCrypt lowers the implementation burden by moving complex cryptographic logic out of Solidity and into replaceable WASM modules, reduces the evaluated calling cost under the experimental gas schedule, and provides a dynamic upgrade mechanism that lets smart contracts evolve their cryptographic capabilities without changing their contract-facing interface. Algorithm execution remains slower than suitable Precompiled Contracts, and the current gas parameters are not economically calibrated. Future work will refine resource pricing and evaluate broader deployment and security conditions.
